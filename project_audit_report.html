一、总体诊断

核心发现：项目呈现"算法强、集成弱"的显著断层。

  • algorithm/ 目录已完成策划方案中 80%+ 的算法模块（感知/评估/干预/升级/隐私/审计/联邦），300 测试全通过
  • client/ 前端仍是独立的 React 应用，未接入任何 Python 算法能力，AI 咨询直接调用通义千问 LLM
  • server/ Node.js 后端与 algorithm/ 零连接，无 HTTP/gRPC 桥接
  • 策划方案中的"前端改进"（同龄对比、实时情绪曲线、安全审计面板等）全部未实现

四、差距清单与改进方案

🔴 关键差距（影响核心功能闭环）

GAP-1：Server ↔ Algorithm 零连接 关键
Node.js 后端与 Python 算法后端完全独立运行。AI 咨询直接调用通义千问，不经过状态机/审计/多任务评估。这意味着 algorithm/ 中所有算法能力对用户完全不可见。
改进方案：
① 在 server/ 中添加 algorithm-bridge 服务层，通过 HTTP 调用 algorithm/ 的 FastAPI 端点
② 或将 algorithm/ 核心逻辑封装为 Python 微服务（已有 api/ 路由），server/ 通过 fetch 调用
③ 修改 ai.service.ts，将 LLM 调用改为经过 AuditedLLMMiddleware 包装
GAP-2：AI 咨询未集成对话状态机 关键
Chat.tsx 直接调用 LLM 生成回复，无状态机控制对话流程、无安全审计中间件拦截、无结构化 Action 输出。策划方案的核心亮点"感知-评估-干预-升级闭环"在前端完全断裂。
改进方案：
① 前端 Chat.tsx 改为调用新的 /api/consultation/smart 端点
② 该端点内部调用 DialogEngine 管理状态 → AuditedLLMMiddleware 包装 LLM → 返回安全回复
③ 前端展示当前对话状态和允许的干预动作
GAP-3：焦虑检测与心理测评未合并 关键
前端 AnxietyDetect.tsx 使用键盘节奏+眨眼频率的纯前端检测，Assessment.tsx 使用 PHQ-9/GAD-7 表单。两者完全独立，且均不接入 Python 多任务风险评估引擎。
改进方案：
① 新建统一的"多任务评估"页面，合并两个入口
② 前端采集文本+语音 → 调用 /api/assessment/predict → 展示 PHQ-9/GAD-7 预估区间
③ 保留前端键盘/眨眼检测作为辅助信号，融合到多任务模型输入

🟡 重要差距（影响方案完整性）

GAP-4：语音/面部/行为感知模块为空 重要
perception/voice/、perception/face/、perception/behavior/ 三个子模块仅有空的 __init__.py。策划方案要求的声学特征（基频/能量/语速/共振峰）、MediaPipe 微表情检测、行为模式分析均未实现。
改进方案：
① voice/：集成 librosa/parselmouth 提取声学特征（至少实现基频 F0、语速、能量 3 项）
② face/：集成 MediaPipe Face Mesh 提取眨眼频率/眉毛运动/嘴角位移
③ behavior/：从平台使用日志提取活跃时段/使用频率/社交互动特征
④ 若时间有限，可先用模拟接口占位，但需有清晰的 extract_features() 函数签名
GAP-5：CBT 认知重构脚本缺失 重要
intervention/cbt/ 目录为空。策划方案要求的 5 步引导流程（识别自动思维→检验证据→寻找替代解释→评估情绪变化→制定行动计划）未实现。
改进方案：
① 在 cbt/ 下创建 cognitive_restructuring.py，实现 5 步引导状态机
② 每步输出结构化引导话术（青少年友好语言）
③ 包含用户拒绝配合的退出机制
GAP-6：SProp GNN 语义盲法未实现 重要
文本情感分析使用标准 RoBERTa fine-tuning，无"语义盲法"去偏见机制。策划方案引用了 Nature Scientific Reports 2026 的 SProp GNN 架构。
改进方案：
① 若无法复现 SProp GNN，可在现有 RoBERTa 基础上添加对抗去偏见训练（adversarial debiasing）
② 或在报告中明确说明"语义盲法为理论方案，当前使用标准 Transformer + 公平性审计后处理"
GAP-7：前端缺少多项策划要求的改进 重要
同龄对比可视化、咨询师端实时情绪曲线、安全审计面板、管理端公平性报告、社区审核页面、隐私控制设置 — 全部未实现。
改进方案（按优先级）：
① 咨询师端安全审计面板 — 展示被拦截的回复和危机升级事件
② 管理端公平性报告 — 调用 /api/audit/fairness 展示分组性能差异
③ 同龄对比雷达图 — 调用 compute_baseline_deviation() 在 Home.tsx 展示
④ 实时情绪曲线 — ConsultantRoom.tsx 中按时序绘制情感变化折线图
⑤ 社区审核页面 — 对接已有的 /api/community/pending API

🔵 改进建议（提升方案竞争力）

GAP-8：PerceptionService 未对接 fusion 模块 建议
fusion/ 子模块有完整的三策略融合实现（加权/Stacking/动态加权），但 PerceptionService 使用独立的简化版加权平均，两者未集成。
修改 perception_service.py 的 analyze_multimodal() 方法，调用 fusion.fuse_multimodal() 替代内联的加权平均。
GAP-9：数字表型数据源全为模拟 建议
phenotype.py 的五类特征提取使用 np.random 模拟数据。策划方案要求对接睡眠监测、对话情感、平台使用日志等真实数据源。
在 server/ 中实现数据获取适配层，从 Prisma 数据库查询真实用户数据，传入 extract_digital_phenotype()。
GAP-10：缺少共病模式分析 建议
策划方案要求管理员端增加"共病模式"分析（如抑郁+睡眠障碍联合预警），当前未实现。
在 assessment/ 中新增 comorbidity.py，分析多任务模型输出的联合风险模式，在管理端展示热力图。

七、结论

项目优势：

  • 算法后端架构完整，"感知→评估→干预→升级"四层闭环逻辑已实现
  • 300 个单元测试覆盖全面，代码质量有保障
  • 隐私保护三层架构（端侧量化→脱敏上传→联邦学习）已落地
  • 公平性审计 + 对比实验为技术报告提供了量化数据支撑

最大短板：

  • 前后端断裂 — algorithm/ 的全部算法能力无法触达用户界面
  • AI 咨询绕过安全链路 — 直接调用 LLM，无状态机/审计/危机拦截
  • 多模态感知不完整 — 语音/面部/行为三个通道为空壳

建议：优先完成 P0（Server 桥接 + Chat 集成状态机），这是将"算法能力"转化为"用户可感知功能"的关键瓶颈。完成 P0 后，策划方案的核心亮点才能在演示中体现。
