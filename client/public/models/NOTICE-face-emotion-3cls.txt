  （12 轮，batch 96，AdamW lr 1.5e-4 余弦退火，标签平滑 0.05）
- 为什么做（第一版）：用户反馈**「咧嘴笑被识别成悲伤」**。实测（`scripts/face_fix_diagnosis.md`）：
  原模型在 96×96 patch 里人脸**上移 4px 就有 35%、上移 6px 有 76.2% 的"开心"被改判成"悲伤"**；
  JPEG q30 下 30% 的开心变悲伤；分辨率降到 1/3 时开心召回只剩 47.5%。
  即失败不是"前端裁错了"，而是模型**过度依赖人脸在 patch 中的绝对位置**。
- 为什么做（第二版）：用户接着反馈**「中性和悲伤分不出来」**。复测确认这**不是第一版的回归**
  —— 第一版在每一格上都优于微调前；但 `webcam`（脸偏小 + 略糊 + 偏色 + 噪声 + 压缩**叠加**）
  这一场景两个模型都不行（真 sad 有 33.8% 被判成中性）。追因：第一版用来**选模型**的 7 种
  干扰里没有这个叠加场景，所以从没被优化过。
  第二版的做法：① 增广里新增**叠加型退化链**（概率 0.45：降采样 → 模糊 → gamma → 白平衡 →
  噪声 → JPEG）；② 把 `webcam` / `webcam_hard` 加进**选模型**用的鲁棒验证集（9 种干扰）。
- 做法（两版共通）：训练时在线施加平移 ±8px / 缩放 0.85–1.18 / 高斯模糊 0–2 / 降采样 /
  JPEG q20–85 / 亮度对比度抖动 / 水平翻转，逼模型不再依赖这些捷径。
  选模型准则：**干净验证精度允许掉 ≤1pp，在此约束下取鲁棒性最好的一轮**（逐轮打印两个指标）。

导出方式（可重跑，产物不入库）
------------------------------
    # 从抗干扰微调权重导出（当前入库版本）
    & "D:\Develop\AIC\.venv\Scripts\python.exe" scripts/export_face_emotion_onnx.py \
        --weights "D:\Develop\AIC\Face\ResNet50_finetuned_v2.pth" \
        --out client/public/models/face_emotion_3cls.onnx

脚本会做三件事并逐条打印证据：
1. 用**手写的 ResNet50**（venv 有 torch 无 torchvision）`load_state_dict(strict=True)`
   加载权重：320 个张量、逐键逐形状对齐，不一致直接失败；
2. 导出 ONNX（opset 17，H/W 为动态维，输入名 `input`、输出名 `logits`）；
3. 用原生 onnxruntime 与 torch 逐尺寸比对：224px 最大绝对差 2.8e-06、64px 2.4e-06。

运行时口径（必须与训练一致）
----------------------------
- 输入：RGB 通道序，`x/255`，NCHW。训练时 transform 是 `Compose([ToTensor()])`，
  **没有 ImageNet 归一化、没有 resize/crop** —— 前端 `packFaceImage` 与之一致。
- 输出：3 个 logits，前端做 softmax 得三类概率。

已知限制（务必如实对待）
------------------------
1. **精度已在本机标定（2026-10-10）**，validation（n=1615，数据集自带划分）：

   | 配置 | 准确率 |
   |---|---|
   | 修前：224px + `happy,neutral,sad` | **40.6%** |
   | 修后：96px + `neutral,happy,sad` | **95.2%** |
   | 抗干扰微调第一版 | 95.5%（全量）/ 95.7%（前端代码路径 n=600） |
   | **抗干扰微调第二版（入库）** | **95.1%（全量）/ 95.8%（前端代码路径 n=600，退出码 0）** |

   交叉验证：`D:\Develop\AIC\Face\ResNet101_best9517.pth` 的文件名恰为 **95.17%**，
   与独立测得值吻合 —— 模型本身没问题，此前掉分全在部署侧的两个常量。

   复核分两层，都要跑：
   (1) 模型侧：`& "D:\Develop\AIC\.venv\Scripts\python.exe" scripts/face_emotion_accuracy_check.py --sizes 96`
       （扫尺寸 × 6 种类别排列 + 混淆矩阵；微调后实测最佳映射仍是 `neutral,happy,sad` 95.5%）
   (2) 前端侧：先 `... --dump-rgba .tmp-face-rgba`，再
       `node "server/node_modules/tsx/dist/cli.mjs" scripts/verify_face_emotion_accuracy.ts --data .tmp-face-rgba`
       —— 这一层跑的是**真正的前端代码**（`classify` → `packFaceImage` → `toReading`），
       实测 **95.7%（n=600，退出码 0）**；加 `--force-input-size 224` 故意配错得
       **40.7%（退出码 1）**，证明它确实能发现问题。
       `tsc` 只保证类型对，**保证不了索引→标签映射的语义**，所以这层不能省。
       `--model` 可指向候选模型：**换模型必须先在这里跑通再覆盖 `client/public/models/`**。
   (3) 鲁棒性侧：`... scripts/face_emotion_domain_shift_check.py --limit 80 --splits validation`
       逐干扰看"开心→悲伤"比例；微调后该比例在所有干扰下均为 **0.0%**（见上方第二段）。
2. **输入尺寸 = 96×96，已实测确定。** 数据集里所有图片原生就是 96×96，
   训练 `Compose([ToTensor()])` 不 resize，故模型只在 96 上训过。
   尺寸扫描：`64→43.6% / 96→95.1% / 128→54.9% / 160→51.6% / 224→40.0% / 256→37.1%`。
3. **测试集含第 4 类 `fear`（606 张），本模型只有 3 类，无法识别。**
   实测 fear 样本 **99.3% 被归到 sad**。在 3 分类可判的样本上准确率 96.2%；
   若把 fear 计入分母，"总体"只有 72.2%，而**上限本来就只有 75%**。
   → 对外不要报 testing 的总准确率；要 4 类（含恐惧）必须重新训练。
4. **95.2% 是数据集上的上限，不是线上指标。** 数据集是裁好的 96×96 人脸；
   前端是"从画面裁人脸框再缩放"，留白比例/光照/角度都不同。
   2026-10-10 做了**上线域体检**（`scripts/face_emotion_domain_shift_check.py`：
   把 validation 图按摄像头真实会遇到的退化逐个施加后再测，n=240），结论：
   - 光照/白平衡几乎无影响：flat 98.3%、wb_warm 98.3%、dark 97.9%、bright 97.9%
     （干净基线 97.5%）→ **不要**去加光照归一化，那只会偏离训练分布；
   - 掉分集中在**细节丢失**：blur1 92.1%、halfres（等效源 48px）90.0%、
     thirdres（等效源 32px）75.4%、blur2 64.6%、jpeg30 68.3%；
   - **开心类对清晰度最敏感，且失败模式就是"被判成中性"**：
     开心召回 clean 96.2% → blur1 83.8% → halfres 77.5% → thirdres 47.5% → blur2 28.7%，
     而 blur2 下有 **68.8%** 的开心样本被判成中性 —— 与"开心几乎识别不出来"的反馈吻合。
   → 界面因此新增 `裁剪源 Xpx → 96px` 读数：X < 96 就是"放大喂模型"，
     并提示"离摄像头近一些"（这是唯一真正有效的可操作建议）；
   → 前端 patch 的降采样质量从默认 `'low'` 改为 `'high'`（默认 `'low'` 在源矩形
     明显大于 96px 时只做 2×2 双线性欠采样，而微笑的嘴角弧度正是高频特征）。
   ⚠️ 报告里的退化都是**构造出来的仿真**，能回答"哪个因素最可能致命"，
   **不能替代真实摄像头采集**。要把线上精度坐实，仍需采集带标签的真实 patch。

4.1 **采样节律已重做（2026-10-10）。** 旧实现 `max(1000ms, 上次耗时 × 2)` 在慢后端上
   把周期抬到 1.2~3 秒（用户反馈"一直在等结果"）。现改为
   `clamp(上次耗时 × 1.15, 60ms, 2000ms)`（`client/src/hooks/faceEmotionPacing.ts`），
   并配套自适应读数有效期（1.5~8s，恒 > 2 个采样周期）与 τ=450ms 的展示平滑
   （上屏用平滑值，判定与风险一律用未平滑的 `probabilities`）。
   改前/改后的刷新率由 `scripts/verify_face_emotion_pacing.ts` 直接算出来：
   后端 30ms 时 6→51 次/5s，600ms 时 5→8 次/5s，1500ms 时 2→3 次/5s。
5. **样本域风险。** 与移动端前置摄像头、逆光、侧脸的分布差异未做评估。
   低照度/大角度时的输出不可当真。
6. **只展示与上报，不参与风险。** 结果写进 `FacialAnalysis.faceEmotion`，
   不进入 `riskScore`/`riskLevel` 融合 —— 与眼状态模型同一条约定
   （阈值类变更需人工审核，见 AGENTS.md 安全红线）。

隐私
----
全程在本机 canvas + WASM/WebGPU 内完成，不传帧、不落盘；与眨眼检测共用同一路
摄像头与同一帧关键点（`useFacialAnalysis` 的指标拍），不新开流、不新开检测器。
慢设备上 wasm 会话跑在 Web Worker 里（`env.wasm.proxy`），不阻塞主线程与眨眼通道。

为什么不入库（与 open_closed_eye.onnx 的处理相反）
--------------------------------------------------
89.62 MB 已接近 GitHub 单文件 100 MB 硬上限，且可由上面一条命令从权重重新导出；
入库会永久占用仓库体积（普通 git）或消耗 LFS 配额（1 GB 免费额度，见 .gitattributes）。
因此 `.gitignore` 仍按 `*.onnx` 忽略本文件，**只放行本说明**。
部署时需要额外一步：跑一次导出脚本，或把该文件随构建产物一起拷贝。
