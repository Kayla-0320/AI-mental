> 评估问题：现有视频功能（摄像头 + 眨眼判定 + 面部分析等）能否融入拟建的实时语音通话功能？

> * **[实测]** —— 本次会话在本机真实跑出来的数字（含一次带真人脸的浏览器测量与一次资源泄漏复现）。
> * **[实测-代码]** —— 从当前工作区文件读到的代码，逐条给了 `文件:行号`。
> * **[未验证]** —— 没验证过的。

## 0. 大白话版（先读这个）

一句话：**能做，难点不在算力。**

本机实测：摄像头和语音同时跑，语音识别速度几乎没变（partial 6.0 ms → 6.1 ms，20 核机器）。
真正的难点是三个，都跟"算得快不快"无关。

### 难点一：摄像头和麦克风没有"主人"

现在开摄像头的代码是这样写的：

```ts
streamRef.current = stream;   // ← 直接覆盖，不先关掉上一个
```

`streamRef` 只记得住**最后一次**开的那条流。所以"再开一次"永远等于"漏一份"——
前一份的轨道还活着（浏览器麦克风指示灯还亮着），但已经没有任何变量指向它，
`stop()` 永远够不到它。

**这不是"用户手快才会碰到"的问题。** 视频通话里"再开一次"是必然发生的，而且大多不用点鼠标：

| 通话中的自动事件 | 结果 |
|---|---|
| 切前后摄像头 | 又一次 `getUserMedia`，旧的没人关 |
| 断线重连 / 挂断后重拨 | 同上 |
| 通话页和眨眼检测各要一路 | 两个消费者抢同一个摄像头 |
| 开发模式下组件重挂载（StrictMode） | 直接双开 |
| 手机来电打断 / 切后台再回来 | 同上 |

（§4.1 的复现用"连点 4 次"只是**最小的显形手法** —— 把"再开一次"在几毫秒内重复 4 遍。
要看的是"每再开一次，旧的有没有被关掉"，不是点击次数。当前唯一的入口
`Profile.tsx:821`「启动分析」按钮**只能开、不能关**，点完还弹窗引导用户重试，
所以连点在这个 UI 上确实是真实用户行为 —— 但那不是它成为问题的原因。）

所以要先做一个"设备管理员"：谁要用摄像头/麦克风都找它借，用完还回来，它记账。
**这是纯工程活，不难，但必须在写通话代码之前做** —— 后补就得在两套打架的逻辑中间插一层。

### 难点二：通话的时候"看脸"不准

视频里真正可信的只有三样（眨眼、头部角度、面部动作原值）。但它们在通话场景会变差：

* **眨眼**：摄像头每秒只看 10 次，而一次眨眼只持续 0.1~0.4 秒，**大部分眨眼根本没拍到**。
  于是"眨眼次数"偏低，系统会把"没测到"当成"走神/解离"。
* **头部角度**：它测的是头的角度、不是眼睛看哪。打电话时低头看手机是常态，
  现有规则会把"低头超过 10 度"当成回避，**会一直误报**。
* **表情**：说话本身嘴就在动，"表情"算出来基本全是发音动作。

解法有三档：把摄像头提到 30fps（更费 CPU）、把指标改名并重调阈值、
或者最简单也最稳的 —— **通话时这些数字只显示、不参与风险判断**。我推荐第三档。

### 难点三：有些数字是编的

这个最省事，因为是**删代码**。

程序里写着"微表情平均持续 200 毫秒"——这是写死的常数，不是测出来的。
还有一个"置信度 = 0.7 + 帧数 × 0.005"，意思是**只要跑了 50 帧就自动变成 0.95**，
跟画面清不清楚、有没有人在镜头里完全无关。

问题是这个假的置信度会一路传到数据库，**改写咨询师看到的患者风险标签**。
放在边缘小卡片上还只是不好看；一旦折进通话这个旗舰功能，它就变成门面读数了。

### 所以

| | 能不能解 | 成本 |
|---|---|---|
| 难点一 设备生命周期 | 能，标准做法 | 小（让 `start()` 幂等 + 一层管理），但**必须先做** |
| 难点二 通话场景下的可靠性 | 能 | 中等，且**建议用"只看不判"绕开** |
| 难点三 常量冒充测量值 | 能 | 极小（删） |

**唯一的硬约束：难点一必须先修。** 这是我唯一会说"不许跳过"的一条。

### 我建议的形态

视频**默认关闭**，做成一个明确开关。通话时视频**只用来"看"，不用来"判断风险"**。

如果只做一个视觉功能，做 **"人还在不在画面里"**（就一个 检测到/没检测到）比做微表情有用得多：
它诚实、便宜、低头走动都不影响，产品含义也真实（"对方还在听吗"）。

## 1. 结论先行

**可以融，但不是"把视频功能搬进通话页"，而是"从视频栈里挑三样真信号、丢掉其余的"。**

三条硬结论：

1. **技术上跑得动。** 本机实测：视频循环占浏览器主线程 **约 14%**，而**流式语音识别延迟完全不变**（partial 6.0→6.1 ms）。
   瓶颈不是 CPU 算力，是**浏览器主线程的启动冻结**和**媒体流的生命周期管理**。
2. **真正必须先修的是一件结构性问题，而且它已经被实测复现了。** 根因是一行代码：
   `streamRef.current = stream` 是**覆盖写**，开新流之前不关旧流，于是"再开一次"必然漏一份（§4.1）。
   把它放大后实测得到 **5 条同时在跑的麦克风轨道 + 3 个 MediaPipe 实例 +
   138 次/秒的泄漏定时器 + 1.7 秒界面冻结**。而在通话里"再开一次"**不需要点鼠标** ——
   切前后摄像头、断线重连、组件重挂载、手机来电打断都会触发。通话页如果再开一路
   摄像头/麦克风，问题会被放大而不是缓解。
3. **最大的风险不是技术，是诚信。** 视频栈里有一部分指标是**常量冒充测量值**，而其中一个常量
   （`facialMetrics.confidence`）**能改写数据库里的患者风险等级**。通话是旗舰功能、摄像头会一直开着、
   评委和用户会盯着看 —— 把空壳放进旗舰功能，等于把问题放到聚光灯下。

### 1.1 三档取舍

| 档 | 内容 | 理由 |
|---|---|---|
| **A. 值得进通话** | MediaPipe **眨眼**（`eyeBlinkLeft/Right` 真值）<br>MediaPipe **头姿**（`facialTransformationMatrixes` 真值）<br>MediaPipe **AU 原值**（模型真输出） | 输入真、公式真。但三条都带前置条件（见 §3） |
| **B. 不该进通话** | rPPG 心率 / 呼吸频率 / 像素回退面部分析 / Python 感知层的摄像头路径 | 假公式或不可达；已有开关挡住一部分，但"挡住"不等于"删掉" |
| **C. 与通话正交，可继续共用** | 昼夜活动、行为激活 | 数据源是时钟和点击，**与摄像头无关**，不受通话影响 |

### 1.2 一个更值得考虑的替代形态（我的建议）

通话场景里最有价值、最便宜、最抗噪的视觉信号**不是**微表情，而是 **"人还在不在画面里"** ——
即 MediaPipe 的 `faceLandmarks.length > 0` 这个布尔值。

* 它诚实（就是一个检测结果，没有可编造的中间量）；
* 它对头部运动、低头看手机、走动都鲁棒（这些恰恰是通话时的常态）；
* 它在产品上有真实含义："对方还在听吗"；
* 它**不**需要 AU 线性组合、不需要眨眼阈值、不需要头姿角度标定。

**如果只做一件事，我建议做这个**，而把眨眼/头姿作为"第二轮再加"的候选。
理由见 §5 的语义冲突分析。

## 2. 技术可行性：实测数字

### 2.1 测量方法

用 CDP 驱动 headless Edge（假麦克风 = 22 秒中文语音循环；人脸 = MediaPipe 官方 `portrait.jpg`
经 canvas `captureStream` 冒充摄像头，**确保 MediaPipe 真的检测到一张脸**）。
在页面里预先包装 `setInterval`、`WebSocket`、`getUserMedia` 与 `requestAnimationFrame`，
分别量到"视频循环每次 tick 的耗时""服务端回报的 ASR 解码延迟""媒体流获取次数与轨道状态"。
每档配置：加载页面 → 静置 6 秒 → 开功能 → 等 14 秒（模型下载/编译）→ 测量窗口 20 秒。

### 2.2 结果

| 指标 | idle（基线） | voice（仅语音） | camera+voice+真人脸 |
|---|---|---|---|
| 全机 CPU（20 核） | 15.9% | 42.2% | 46.6% |
| 视频循环 tick 数 / 窗口 | 0 | 0 | 334（20s） |
| **tick 平均耗时** | — | — | **13.9 ms**（p95 15.0 ms） |
| tick 最大耗时 | — | — | 142 ms（首次模型编译） |
| 主线程被视频占用 | 0% | 0% | **≈14%** |
| ASR partial 延迟 平均 | — | **6.0 ms** | **6.1 ms** |
| ASR partial 延迟 p95 | — | 6.6 ms | 7.1 ms |
| ASR final 延迟 平均 | — | **52.0 ms** | **53.9 ms** |
| partial 数量 | — | 62 | 66 |
| 主线程长卡顿（>50 ms） | 0 帧 | 1 帧 | 2 帧 |
| MediaPipe 初始化 | — | 不初始化 | ✅ 成功 |

**三条读数：**

1. **音频链路零退化。** 加上摄像头 + 真人脸 + MediaPipe 全量推理后，ASR partial 延迟从
   6.0 ms 变成 6.1 ms（+0.1 ms），final 从 52.0 变成 53.9 ms（+1.9 ms，在噪声范围内）。
   全机 CPU 只涨了 4.4 个百分点（20 核里不到 1 个核）。
   → **瓶颈不在算力。**
2. **视频本身的代价在主线程，不在 CPU。** 每次 tick 13.9 ms / 100 ms 间隔 = 14% 主线程。
   在 10 fps 下这个量级是健康的。
3. **启动那一下会冻结界面。** 首次 tick 142 ms；把 MediaPipe 模型编译与多次重复初始化叠加时，
   实测到 **1.5–2.3 秒**的主线程冻结（`rafMaxGapMs` 1518 / 1702 / 2350 ms）。
   在"按下通话按钮"那一刻冻结两秒，是通话体验里的真问题。

### 2.3 MediaPipe 到底能不能用 —— 能，但依赖外网且未锁版本

之前我误以为 Google 系被墙。**实测两个地址都可达**：

| 依赖 | 地址 | 实测 |
|---|---|---|
| WASM（11.7 MB） | `https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@latest/wasm` | HTTP 200，11756954 B |
| 人脸模型（3.8 MB） | `https://storage.googleapis.com/mediapipe-models/face_landmarker/...float16/1/face_landmarker.task` | HTTP 200，3758596 B |

浏览器里实测初始化成功：`[面部分析] ✅ MediaPipe Face Mesh 初始化成功`。

**但有两个真实风险** [实测-代码 `useFacialAnalysis.ts:111-127`]：

* **`@latest` 未锁版本** —— CDN 上的 tasks-vision 升级后，与本机安装的 `1.0.1` 可能 ABI 不匹配。
  而讽刺的是 `node_modules/@mediapipe/tasks-vision/wasm/` **本地就有 1.0.1 的 wasm**（11.7 MB），
  代码却不用它。
* **首帧依赖外网** —— 断网/内网/答辩现场网络抖动 → 初始化失败 → **静默降级**（见 §3.3）。
* 另外：页面加载时就会去拉这两个地址吗？**不是**。实测仅开语音时 `MediaPipe 不初始化`、
  只有 1 次 `getUserMedia(audio)`，说明面部分析确实是随摄像头开关启动的，**没有自动开摄像头**。
  （我最初的一次测量看到语音模式下也有 MediaPipe 日志，是新浏览器 + 旧页面状态残留造成的，
  已用全新浏览器复测排除。）

### 2.4 这次测量**没有**覆盖的东西

| 缺口 | 影响 |
|---|---|
| **TTS 那一腿完全没测** | 计划里的本地 TTS 走 Python CPU，和 ASR 抢同一批核。本次只测了"浏览器视频 + Python ASR"。ASR+TTS+视频三者并存的实际余量**未知** |
| **20 核不代表用户机器** | 本机是 Intel Core Ultra 7 255HX（20 物理核）。普通学生笔记本 4–8 核 + 弱核显，主线程 14% 与 CPU 余量都会显著变差 |
| **假摄像头帧率固定** | canvas 以 15 fps 供流，与真实摄像头（通常 30 fps）不同；真实摄像头会略微增加解码开销 |
| **未测 30 fps 视频** | 若按 §3.1 把眨眼提到 30 fps，视频成本约 ×3（→ 主线程 ~40%），**未验证** |

## 3. 逐项取舍与前置条件

### 3.1 值得进通话的三样，但各带一个前置条件

| 信号 | 为什么值得 | 前置条件 |
|---|---|---|
| **眨眼** `eyeBlinkLeft/Right` → `blinkScore = min(左, 右)` | 唯一"输入真、公式真"的摄像头指标。是 MediaPipe blendshape 的直接输出，不是 EAR 阈值猜的 | ⚠️ **通话期必须把采样率提到 ≥30 fps**。现在视频循环固定 100 ms（10 fps），而人一次眨眼闭眼期 100–400 ms → **大部分眨眼整段落在两帧之间，根本采不到**。结果 `blinkRate` 系统性偏低，会命中 `blinkRate < 8` 的"眨眼过少 → 解离"风险分支 —— **采样不足被解释成心理风险，是方向性错误** |
| **头姿** `headPitch/headYaw` | 由 `facialTransformationMatrixes` 真算出来的角度 | ⚠️ **必须改名**。它叫 `downwardGazeRatio` / `attentionScatter`，但它是**头部姿态不是注视方向**（没有虹膜跟踪）。通话时用户会低头看手机、转头看别处，这些都会被算成"回避/注意力涣散"并**直接加 riskScore**（`>0.5` / `>0.6` 两档硬阈值）。代码里已经诚实地加了 `poseProxy: true` 标注 —— 但标注不能替代改名和调阈值 |
| **AU 原值** | MediaPipe blendshape 的直接输出，可信 | ⚠️ **只上屏、不下结论**。现在 AU 会被手写的线性组合（`au6*0.5 + au12*0.5` 再乘 `1.5/0.4/1.3` 这类拍出来的系数）映射成"情绪"，再进融合。这些系数没有任何验证依据 |

### 3.2 不该进通话的

| 项 | 判定 | 依据 |
|---|---|---|
| **rPPG 心率 / HRV** | **空** | 绿通道三点局部极大计数（无滤波、无频域判定），且 `durationSec = 30/10 = 3` 硬编码而缓冲区累积到 180 点；HRV 更是 `max(5, 50 - |HR - 基线| * 0.5)` 纯拟合。**网络摄像头在普通室内光下测不了 HRV**（RMSSD 需要逐搏毫秒级精度，30 fps 量化 = 33 ms，误差大于被测量本身）。已被 `RPPG_AVAILABLE` 关闭，**保持关闭** |
| **呼吸频率** | **空** | 麦克风 RMS 过零率，且 `/10` 的"假设 10 fps"与实际 ~60 fps 不符（量纲差 6 倍）。已被 `BREATHING_AVAILABLE` 关闭。计划里已给出正确替代：**改用 ASR 的停顿/气口节奏** —— 那才是通话天然产出的数据 |
| **像素回退面部分析** | **半空 + 会静默掐断整条链** | 固定矩形坐标（`{x:40,y:25,w:80,h:20}`）+ 任意 AU 映射；**且从不调用 `onFrameSignal`** → MediaPipe 不可用时眨眼/头姿整条链**静默失效**（`isMeasuring` 永远 false），既不是 0 也不是报错，UI 无任何提示 |
| **Python 感知层的摄像头路径** | **线上不可达** | `AnalyzeRequest` 只有 `text / wav_path / facial_features / behavior_features / age_group / age / user_id`，**没有** `eye_features / hrv_features / breathing_features / circadian_features`。前端三处调用只发 `{text}`。`eye/eye_tracking.py`、`physiological/rppg_hrv.py`、`breathing.py`、`circadian/`、`behavioral_activation/`、`face/facial_expression.py`、`fusion/hierarchical_fusion.py` 全部**不可达** |

### 3.3 藏在"不可达"后面的一个潜伏缺陷（值得顺手删）

`server/src/services/algorithm-bridge.ts:614-627` 传的是**硬编码假值**：

```ts
facialFeatures = { brightness: 128, contrast: 50 };  // 注释写"真实场景应使用 face-api.js"
```

而 `FacialFeatures` 数据类里**不存在**这两个字段 → 被 `hasattr` 过滤掉 → 得到一个全默认对象 →
`features_to_emotion_risk` 返回 `risk_score = 0.0`（**不是 None**）→ 被当成有效模态塞进融合，
造出一个 `[0.4, 0, 0, 0, 0.6]` 的"快乐+中性"层，**会把融合焦虑分往下拉**。

今天它是潜伏的（只有 `/algorithm/perception/upload` 能到，而前端无调用）。
但通话功能如果要把视频特征送到算法层，**第一件事就是别走这条已有假值的路**。

## 4. ⚠️ 必须先修的结构问题（已实测复现）

这一节是整个评估里**最需要行动**的部分。摄像头/麦克风的生命周期管理现在是坏的，
而通话功能恰恰要再开一路摄像头 + 一路麦克风。

### 4.1 泄漏复现（实测，全新浏览器，单次脚本）

操作（**"连点"是为了让问题显形的放大手段，不是用户真实操作**）：
点一次摄像头按钮 → 等 3 秒 → 在 3 秒内连点 4 次摄像头按钮 → 等 6 秒。

用"连点"只是因为它是最小的复现手法 —— 把"再开一次"这个动作在几毫秒内重复 4 遍。
要看的**不是点击次数，而是"每再开一次，旧的那份有没有被关掉"**。

```
getUserMedia 调用：
  t=6017ms  +audio -> 0v/1a      ← 正常开启那一次
  t=9040ms  +audio -> 0v/1a      ┐
  t=9040ms  +audio -> 0v/1a      │ 连点 4 次 → 又开 4 路麦克风
  t=9040ms  +audio -> 0v/1a      │
  t=9041ms  +audio -> 0v/1a      ┘

轨道存活状态（每一条都是 live，没有一条被 stop）：
  stream#0 audio=live
  stream#1 audio=live
  stream#2 audio=live
  stream#3 audio=live
  stream#4 audio=live
  → liveTrackCount = 5

MediaPipe 初始化成功日志：3 次
视频循环真实频率：1376 tick / 10 秒 = 138 次/秒（应该是 10 次/秒）
主线程最长冻结：1702 ms
```

**根因（一行）**：`useFacialAnalysis.ts:479` 与 `useVoiceAnalysis.ts:283` 都是

```ts
streamRef.current = stream;   // 覆盖写，不先 stop 旧的
```

`streamRef` 只记得住最后一次开的流，前面几份的轨道仍然 `live`（浏览器麦克风指示灯亮着），
但已无任何引用可达，`stop()` 永远够不到它们。`intervalRef.current` 与 `faceLandmarkerRef` 同理：
约 14 个视频循环定时器同时在跑、3 个 MediaPipe 实例只有最后一个能被 `close()`。

**为什么 4 次点击都进了"开"分支** —— 两条互相独立的放大路径：

* `AnxietyContext.tsx:967` `toggleCamera` 没有重入保护，且 `setCameraEnabled(true)` 是在
  `await Promise.all(...)` **之后**才执行；在 await 期间 `cameraEnabled` 仍是 `false`，
  后续点击继续走"开"分支。
* `AnxietyContext.tsx:511` `handleStart`（`start-multimodal-analysis` 监听器）**完全没有守卫**，
  每次调用都真的再开一路 `voice.start()` + `facial.start()`。目前唯一触发点是
  `Profile.tsx:821` 的「启动分析」按钮：它**只能开、不能关**，点完还会 `alert`
  "如果还是没有变化，请检查摄像头/麦克风权限" —— 等于在引导用户再点一次。

> **所以问题的性质不是"用户手快"，而是"这个入口只能进不能出"。**
> 在通话页里后果一样，但触发方式会换成 §0 难点一列出的那些自动事件。

**这不是理论风险，是复现出来的。** 在 20 核机器上 ASR 延迟仍然只有 6.0 ms（所以不会立刻崩），
但它意味着：麦克风指示灯关不掉、CPU 白烧、内存不回、界面卡顿。

### 4.2 通话页会把它放大

仓库里现在有 **5 个独立的 `getUserMedia` 调用点**：
`useFacialAnalysis.ts:476`（video）、`useVoiceAnalysis.ts:282`（audio）、
`useBlinkDetection.ts:207`（video，**死代码**）、`usePerception.ts:69`（audio，**死代码**）、
`PatientRoom.tsx:84`（audio）、`useWebRTC.ts:98` 与 `:194`（video+audio）。

如果按现有 WebRTC 接法接通话，而用户此前已在聊天页开过"多模态感知"：
**2 路摄像头 + 2~3 路麦克风 + 2~3 个 AudioContext 同时存活**，两套清理逻辑互不知情。

> **结论：在抽出一个 `MediaStreamManager`（单例 + 引用计数 + 统一 `getUserMedia`/`stop`）之前，
> 不要开始写通话页的媒体代码。** 这不是"可以后补的重构"，而是先决条件 ——
> 后补意味着要在两套已经互相打架的清理逻辑中间插一层。

### 4.3 顺带要修的两个小事（都很便宜）

1. **让 `start()` 幂等**（这是根因，单独做就能消掉"再开一次漏一份"）：
   在 `useFacialAnalysis.ts:474` 与 `useVoiceAnalysis.ts:280` 的 `start()` 开头先
   `streamRef.current?.getTracks().forEach(t => t.stop())`，并清掉旧的 `intervalRef` / `AudioContext`。
2. **给两个启动入口补守卫**：`toggleCamera` 加重入锁（`setCameraEnabled` 不要等 await 之后才置位）、
   `handleStart` 加 `isRecording / isDetecting` 判断（`startVoiceInput` 已有这个判断，摄像头侧没有）。
3. **给「启动分析」按钮一个真正的关闭态**，或直接删掉它、统一走 `toggleCamera` ——
   它现在只能开不能关，还用 `alert` 引导用户重试。
4. **删掉死代码** `useBlinkDetection.ts`（10 KB，会自己再开一路摄像头 + 第二个 FaceLandmarker
   + 自己的 rAF 循环，但全仓导入点为零）和 `usePerception.ts`。留着它们等于留着两个未来的事故源。

## 5. 语义与产品层面的冲突（我认为最值得想清楚的一层）

技术能跑通不等于应该做。有三点值得在动手前想清楚。

### 5.1 "打电话"和"开着摄像头"是两种不同的心理契约

豆包的电话功能**不要求你看着屏幕**。而一旦通话界面里出现摄像头预览与"眨眼 12 次/分"这样的读数，
用户理解的就不只是"我在打电话"，而是"**它一直在看我**"。对青少年心理服务来说，这两者的
自我披露程度差别很大 —— 前者的默认预期是可以躺着、走神、沉默；后者会让人坐直、对着镜头。

这也正好和项目已有的诚实口径一致：`perceptionCapabilities.ts` 的文件头写着
"如果仍然让它们输出数值，那些数值只能来自噪声或凭空推算，会被用户/咨询师误当成真实测量结果"。
**通话是可见度最高的地方，这里更该保守。**

### 5.2 通话场景会让视觉指标变得更不可靠，而不是更可靠

通话时用户会走动、低头看手机、转头、离开画面、光线变化。这些对摄像头指标的影响是：

| 指标 | 通话场景的问题 |
|---|---|
| 眨眼 | 10 fps 已经系统性偏低；头部运动 + 离开画面会进一步漏采 |
| 头姿 | "低头"在通话里是**常态**（看手机、记笔记），不是回避信号。现有阈值 `pitch > 10°` → 加风险分，在通话里会**持续误报** |
| AU / 表情 | 说话本身会大幅改变下半脸 AU（`jawOpen`、`mouthSmile`）→ 通话时"表情"几乎全是发音动作，不是情绪 |

**通话是视觉情绪识别的坏场景。** 坐着打字聊天时摄像头信号干净得多。

### 5.3 而它们现在能改写数据库里的风险标签

这条链路是本次审计里最需要复核的一条 [实测-代码]：

```
facialMetrics.confidence = min(0.95, 0.7 + frameCount * 0.005)   ← 帧计数常量，非信号质量
  ↓  AnxietyContext.tsx:631-633   weights.facial = clamp(confidence * fusionConfig.facial)
  ↓  fusedProbs → anxietyProb → riskLevel        (AnxietyContext.tsx:808-811)
  ↓  reportToServer                              (AnxietyContext.tsx:1055)
  ↓  POST /api/profile/anxiety-report
  ↓  prisma.patientProfile.update({ riskLevel }) (profile.controller.ts:191-197)
```

也就是说：**一个"跑了 50 帧就饱和到 0.95"的置信度常量**，经融合后可以改写
咨询师/管理员看到的患者风险等级。它不弹危机窗（弹窗只认服务端字段），但会改标签。

同类常量还有一个：`microExpressions.avgDuration = 200`（有过一次计数就恒为 200 ms）。

**这两条与通话无关，但"把视频折进通话"会让它们从边缘卡片升格成旗舰功能的核心读数 ——
所以先把它们删掉，再谈融合。**

## 6. 建议的实施顺序

### 阶段 A：通话之前的**前置修复**（不做完不碰通话媒体代码）

| # | 事项 | 为什么是前置 |
|---|---|---|
| A1 | 抽 `MediaStreamManager`（单例 + 引用计数），感知 hook 与 WebRTC 共用轨道 | §4.1 已实测泄漏；通话页会再开一路 |
| A2 | **让 `start()` 幂等**（开新流前先 `stop` 旧流），再给 `toggleCamera` / `handleStart` 补重入守卫 | §4.1 根因：`streamRef` 覆盖写 → 每次"再开一次"漏一份；通话里的"再开一次"是自动事件 |
| A3 | 删死代码 `useBlinkDetection.ts` / `usePerception.ts` | 各自会开独立摄像头/麦克风 |
| A4 | 删 `microExpressions.avgDuration = 200` 与 `confidence = 0.7 + n*0.005`，改为**如实上报信号质量或直接留空** | 常量冒充测量，且能改写患者风险标签 |
| A5 | 把 `downwardGazeRatio` / `attentionScatter` 改名为 `headDownRatio` / `headYawStd`，并重设阈值（通话场景下 `pitch>10°` 不成立） | 构念错误 + 通话时持续误报 |
| A6 | 加"视觉能力不可用"的 **UI 状态**（现在只 `console.warn`，静默降级到像素法且静默掐断眨眼链） | 答辩现场断网时，用户与评委都不知道发生了什么 |
| A7 | 把 MediaPipe 的 wasm 改为用**本地 `node_modules` 副本**（已有 1.0.1），版本号锁死 | 消除 `@latest` 漂移 + 减少 11.7 MB 外网依赖 |
| A8 | 删 `algorithm-bridge.ts:620-623` 的 `{brightness:128, contrast:50}` | §3.3：造出一个假的"快乐"模态，会把焦虑分往下拉 |

### 阶段 B：通话页里的视觉（可选，且**默认不融合**）

| # | 事项 |
|---|---|
| B1 | 通话页**默认关闭视觉**；视觉是一个显式开关，UI 上写明"开启后摄像头画面会被本机分析" |
| B2 | 通话期**把视觉指标排除在融合与风险判定之外**（只上屏展示，不进 `weights`、不进 `riskLevel`、不上报） |
| B3 | 通话期把面部分析提到 **≥30 fps**（否则眨眼数据不可用）——注意实测视频成本约 ×3，**未验证** |
| B4 | 若要做"存在感"信号，用 `faceLandmarks.length > 0` 这个布尔值（§1.2），不要用 AU/眨眼/头姿 |

> B2 是最关键的一条。理由是 §3.1 + §5.2：通话时视觉指标的可信度**下降**，
> 而它们能改写风险标签。让它"只展示不决策"，既不牺牲通话观感，也不引入误报。

### 阶段 C：明确不做

* ❌ rPPG 心率 / HRV（物理上不成立，保持 `RPPG_AVAILABLE = false`）
* ❌ 呼吸频率（改由 ASR 停顿/气口节奏推断 —— 那才是通话的天然产物）
* ❌ 像素回退面部分析（固定矩形 + 任意映射 + 静默掐链路）
* ❌ Python 感知层的摄像头路径（不可达；要用就先扩 `AnalyzeRequest`，但那是一条独立的工作线）
* ❌ 把 `useBlinkDetection` 复活（它是死代码，且设计上会开第二路摄像头）

## 8. 一页速览

1. **跑得动**：实测视频循环占主线程 ~14%，而**流式 ASR 延迟零退化**（6.0 → 6.1 ms）。瓶颈不是算力。
2. **但先修媒体流管理**：根因是 `streamRef.current = stream` 覆盖写（开新流不关旧流），
   所以"再开一次"必然漏一份。放大后实测 **5 条 live 麦克风 + 3 个 MediaPipe 实例 +
   138 次/秒泄漏定时器 + 1.7 s 冻结**。通话里"再开一次"是自动事件（切摄像头/重连/重挂载），
   抽 `MediaStreamManager` + 让 `start()` 幂等是通话的**先决条件**，不是可后补的重构。
3. **只挑三样真信号**：眨眼、头姿、AU 原值 —— 且各带前置条件（眨眼要提帧率、头姿要改名、
   AU 只上屏不下结论）。
4. **删掉常量冒充测量的两项**：`microExpressions.avgDuration = 200`、
   `confidence = 0.7 + frameCount*0.005`。后者能**改写数据库里的患者风险等级**，
   而通话会让它变成旗舰功能的核心读数。
5. **通话是视觉情绪识别的坏场景**：低头看手机、说话带动下半脸、走动离开画面 ——
   这些在通话里是常态，却会被现有阈值判成回避/注意力涣散。
6. **建议形态**：视觉默认关闭、且**只展示不参与风险判定**；如果只做一个视觉信号，
   做"人还在不在画面里"这个布尔值，而不是微表情。
