# AI 偶尔"先说一句乱话、再说正文"：两条候选机制与已加的守卫

> 用户口径（2026-10-11）：**"AI 回复时偶尔会说出一些乱说的话，然后才能说出回复的内容。"**

这是**听觉现象**的描述，它至少对应两条完全不同的机制，而且处置方式相反。
所以本轮先做两件事：**把两条机制各自的证据摆到面板上**，并对其中一条**可证明**的
加上有界守卫。**没有改模型、没有改音质参数、没有改切分规则。**

## 1. 两条候选机制（必须先分清的）

| 机制 | 听感 | 判据（现在放在哪） |
|---|---|---|
| **A. 短片段被单独合成** | 先冒出一句**很短的、莫名其妙的**话，然后才是正文 | 面板 `短单元(<4字)` / `短单元已拦住` / `合成段数` |
| **B. 送合成/念出的文本不是屏幕上那句** | 说出的是**别的内容**（可能与上一轮有关），然后正文 | 面板 `TTS·文本不一致` + 请求/念出样例 |

A 是**切分切在了不成立的位置**（文本没错）；B 是**文本来源错了**（内容不对）。
两者都不能靠"再听一遍"分辨，必须看读数。

## 2. 机制 A：短片段独立合成 —— 已修（有界守卫）

### 为什么必然会发生

`onDelta` 的 **delta 回退路径**会把"宽限期到点时手上已有的 delta"送去合成，
而 delta 是**逐字**到达的：

```
t=0     模型开始吐字： 「嗯」        ← 第一个 delta
t=350   宽限期到点（speak 计划实测从未在宽限内到达）→ 送合成
        ⇒ 服务端把「嗯」当成一个完整句子合成 → 用户先听到一句突兀的短话
t=…     后续 delta 继续到达 → 正文逐段合成 → 用户才听到"正文"
```

`splitSpeakable` 只治理"一段太长"（按 100 字硬切），**管不了"太短"** ——
服务端也没有义务拒绝两三个字。所以"短片段被当成一句话念出来"是当前架构的必然产物。

### 修法（`useVoiceCall.flushByDelta` + `MIN_FIRST_UNIT_CHARS = 6`）

```
首段 trim 后 < 6 字？
  ├─ 是，且本轮还没扣过 → **放回队列**，再等一个宽限期凑齐（ledger 记一笔）
  │                       └─ 又等满仍不够 → **照原样送出去**（绝不长期扣住、绝不丢字）
  └─ 否 → 照原样送合成
```

三条边界（都在回归里钉死）：

* **一个字都不丢**：扣住的是"放回队列 + 再等一次"，不是丢弃；
* **最多白等一个宽限期**（默认 350ms，即实测的纯等待那 350ms）；
* **一轮只扣一次**，绝不会把文本长期压住。

回归：`scripts/verify_short_unit_guard.ts`（5 组，重点是**文本守恒**：
逐字拼接必须等于原文，4/5/6/7 字的边界逐档断言）。

面板新增两行：
`短单元(<4字) = N 个 · 最短「…」`（本轮真的送出过几个短单元）、
`短单元已拦住 = 是/否`（守卫是否真的拦下过 —— 为"是"就证明机制 A 在你这台机器上确实发生）。

## 3. 机制 B：文本来源错了 —— 只加了证据，**没有改行为**

真机上"念出来的不是屏幕上那句"有三条已知来源，各自已有读数：

| 来源 | 现有读数 |
|---|---|
| 审计改稿后旧稿仍在念 | `改稿/未朗读`、过程记录的「安全审计已改稿」 |
| 两个合成来源同时入队（计划 + delta） | `对账·不一致`、`TTS·say 发出` vs `start/end` |
| seq 串单 / 音频串到别的片段 | 面板新增 **`TTS·文本不一致` + 请求/念出样例** |

新增的这一格是**给机制 B 定性的关键**：它把服务端回的 `spoken_text` 与本次
`say` 请求的文本逐条比对，命中就把"请求了什么 / 实际念出什么 / 为什么"
（`疑似串单` / `文本与请求不一致`）摆到面板上（最多 3 组）。
**术语规范化那类预期差异也会计入**，所以要看样例内容才能判定是不是真异常。

## 4. 下一步怎么判（一次通话就能分流）

1. 打一通，出现"先说一句乱话"时记下**那一下的听感**；
2. 看面板：
   * `短单元已拦住 = 是` 或 `短单元(<4字) > 0` → **机制 A**（本轮的守卫就是治它）；
   * `TTS·文本不一致 > 0` 且样例里「请求」与「念出」明显不同 → **机制 B**，把样例原文发出来；
   * 两者都为 0 → 那就是**模型侧的发音/韵律问题**（既不是切分也不是来源），
     下一步要抓的是那段音频本身（需要录音或服务端日志）。
3. 已知的第三个可能：**`speak` 计划迟迟不到**时首段会走 delta 回退，
   而回退的切分位置由"到达时机"决定 —— 这类短片段现在会被守卫扣住，
   如果扣住后听感好转，就确认是机制 A。

## 5. 与其它改动的边界

* **不动**：`hop`、`TTS_SPEED`、`CROSSFADE_MS`、ASR 判停、350ms 宽限（默认值不变）；
* 短单元守卫只影响"什么时候把首段送去合成"，不影响文本内容与音质；
* 过程中所有相关读数都进诊断面板，改任何一项前后都能对比。
