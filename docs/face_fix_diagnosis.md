# 「咧嘴笑被识别成悲伤」—— 根因诊断与修法（2026-10-10）

> 用户反馈两点：① 面部识别间隔太长、一直在等结果；② **咧嘴笑被识别成悲伤**。
> ① 的修法见 `docs/face_emotion_model_integration.md` §6.5（采样节律重做）。
> 本文只讲 ②，全部结论都有本机实跑的数字支撑，命令都附在下面。

---

## 0. 一句话结论

**前端没有裁错，模型本身太脆**：这个三分类模型对**人脸在 patch 里的纵向位置**极度敏感 ——
0px 时开心召回 96.2%，**上移 4px 就有 35%、上移 6px 有 76.2% 的开心被改判成"悲伤"**。
所以线上任何让它"看起来偏了一点"的因素（压缩伪影、分辨率不足、几何偏差、角度），
都会以「咧嘴笑 → 悲伤」这种形式暴露出来。

修法分两层，**都已做完并验收**：

| 层 | 改法 | 状态 |
|---|---|---|
| 前端几何 | 裁剪框纵向比例按实测校正，把系统性偏差从 2.1px 压到 ~0 | ✅ `client/src/hooks/facePatchCanvas.ts` |
| **模型 · 第一轮** | **抗干扰微调**（随机平移/缩放/模糊/降采样/JPEG），修「咧嘴笑→悲伤」 | ✅ 该症状在全部干扰下归零（§3.1） |
| **模型 · 第二轮** | 增广加**叠加型退化链**，并把叠加场景纳入**选模型**指标，修「中性/悲伤分不清」 | ✅ **已入库**：`webcam` 下真 sad 被判成中性 33.8% → **3.8%**（§5.2） |

**结果**：①「开心 → 悲伤」在全部 10 种干扰下从最高 76.2% 降到 **0.0%**；
②「真 sad → 中性」在最关键的叠加场景从 **33.8% 降到 3.8%**。

"仅靠前端调参"是修不掉这个问题的：实测表明位置偏差 2px 以内无害、4px 就崩，
而线上抖动一定超过 2px。必须让模型本身对这类干扰鲁棒。

## 2. 模型到底脆在哪里（逐个干扰单独施加，validation n=240）

命令：

```powershell
& "D:\Develop\AIC\.venv\Scripts\python.exe" scripts/face_emotion_domain_shift_check.py `
    --limit 80 --splits validation
```

每格 = 总体 / 开心召回；「开心→悲伤」是**真实为开心**那批样本被改判成悲伤的比例。

### 2.1 纵向位置（最致命）

| 人脸在 patch 内 | 总体 | 开心召回 | 开心→悲伤 |
|---|---|---|---|
| 0px（数据集口径） | 97.5% | 96.2% | 0.0% |
| 上移 1px | 97.1% | 97.5% | 0.0% |
| **上移 2px（前端改前偏差）** | 92.9% | 95.0% | 0.0% |
| 上移 3px | 84.2% | 86.2% | 3.8% |
| 上移 4px | 65.4% | 52.5% | **35.0%** |
| 上移 6px | 43.3% | 11.2% | **76.2%** |
| 下移 6px | 71.7% | 73.8% | 0.0%（倒向中性） |
| 左右移 6px | 96.2–97.5% | 93.8–95.0% | 0.0% |

**只有"人脸偏高"会倒向悲伤**，而且是断崖式的。这正是用户症状的指纹。

### 2.2 清晰度 / 压缩

| 干扰 | 总体 | 开心召回 | 开心→悲伤 |
|---|---|---|---|
| clean | 97.5% | 96.2% | 0.0% |
| blur1（高斯半径 1） | 92.1% | 83.8% | 0.0% |
| blur2 | 64.6% | 28.7% | 2.5% |
| 分辨率 1/2（等效源 48px） | 90.0% | 77.5% | 0.0% |
| 分辨率 1/3（等效源 32px） | 75.4% | 47.5% | 8.8% |
| **JPEG q30** | 68.3% | 60.0% | **30.0%** |
| webcam（叠加） | 72.5% | 65.0% | 0.0% |
| webcam_hard（+JPEG） | 60.0% | 13.8% | **23.8%** |

失败方向有两支：**模糊/低分辨率 → 中性**，**压缩伪影 → 悲伤**。

### 2.3 光照（可以先排除）

| 干扰 | 总体 | 开心召回 |
|---|---|---|
| dark（gamma 1.35） | 97.9% | 96.2% |
| bright（gamma 0.75） | 97.9% | 97.5% |
| flat（对比度 ×0.6） | 98.3% | 97.5% |
| 暖光 / 冷光 | 98.3% / 97.5% | 98.8% / 96.2% |

**结论：不要去加均值方差归一化或白平衡补偿**，那只会偏离训练分布
（训练 transform 只有 `Compose([ToTensor()])`）。

### 2.4 模型几乎只靠"嘴"判"开心"

| 干扰 | 总体 | 开心召回 | 悲伤召回 |
|---|---|---|---|
| clean | 97.5% | 96.2% | 98.8% |
| **抹掉眼/眉区（上 40%）** | 90.8% | **97.5%** | 81.2% |
| **抹掉嘴区（下 35%）** | 71.7% | **17.5%** | 100.0% |
| 两块都抹掉 | 66.2% | 3.8% | 97.5% |

抹掉眼睛对"开心"几乎无损（甚至略升），抹掉嘴部则直接塌到 17.5%。
→ "开心"完全建立在嘴部高频细节上，所以任何破坏嘴部细节/位置的东西都会改写结论。

### 2.5 类别与"干扰因素"是混杂的

数据集里 `sad` 的人脸包围盒高占比中位数是 **0.7738**，而 `happy` 只有 **0.6440**
（`face_framing_audit.py`）。也就是说模型完全可以靠"脸裁得紧不紧"来猜类别 ——
这是**捷径**，不是表情。`testing/fear` 有 **99.3%** 被归到 sad，也说明 sad 是个"垃圾桶类"。

## 3. 修法：抗干扰微调

脚本：`scripts/finetune_face_emotion_robust.py`

- 在原权重 `ResNet101_WholeData.pth`（实为 ResNet50，`load_state_dict(strict=True)` 逐键对齐）上**小学习率微调**；
- 训练时在线施加**正好对应上面失效模式**的干扰：平移 ±8px、缩放 0.85–1.18、
  高斯模糊 0–2、降采样 0.5–0.9、JPEG q20–85、亮度/对比度抖动、水平翻转；
- 标签平滑 0.05（数据集里 sad 混进了 fear/surprise，硬标签会把这些噪声当真理拟合）；
- 选模型：**干净验证精度允许掉 ≤1pp**，在该约束下取"鲁棒验证"最好的一轮；
  两个指标都会逐轮打印，不允许偷偷用鲁棒性换掉干净精度。

命令：

```powershell
& "D:\Develop\AIC\.venv\Scripts\python.exe" scripts/finetune_face_emotion_robust.py `
    --epochs 12 --batch 96 --lr 1.5e-4 --workers 0 `
    --out "D:\Develop\AIC\Face\ResNet50_finetuned_robust.pth"
```

> `--workers` 必须为 0：本机实测 `workers>0` 会在 Windows 上直接挂住（不是慢）。
> 单进程下增广 1.8ms/张，11300 张 ≈ 20s/轮，够用。

基线（未微调，全量 validation n=1615）：**干净 95.23% / 鲁棒 72.08%**；
混淆矩阵 `neutral 93.2% / happy 92.3% / sad 99.5%`。

### 3.1 实测结果：症状被消除，且干净精度不降反升

12 轮微调，**选中的是第 12 轮**（每轮都打印干净/鲁棒两个指标，逐轮可见）：

| | 干净验证（n=1615） | 鲁棒验证（7 种干扰 × 每类 80 张） |
|---|---|---|
| 微调前 | 95.23% | 72.08% |
| **微调后（已入库）** | **95.60%** | **94.40%** |

逐干扰对照（validation n=240，同一套退化算子，格式 = 总体 / 开心召回 / **开心→悲伤**）：

| 干扰 | 旧模型 | 新模型 |
|---|---|---|
| clean | 97.5% / 96.2% / 0.0% | 95.4% / 93.8% / **0.0%** |
| **上移 4px** | 65.4% / 52.5% / **35.0%** | 96.2% / **96.2%** / **0.0%** |
| **上移 6px** | 43.3% / 11.2% / **76.2%** | 95.8% / **95.0%** / **0.0%** |
| blur1 | 92.1% / 83.8% / 0.0% | 96.7% / 97.5% / 0.0% |
| blur2 | 64.6% / 28.7% / 2.5% | 92.9% / **92.5%** / 0.0% |
| 分辨率 1/2 | 90.0% / 77.5% / 0.0% | 95.8% / **97.5%** / 0.0% |

**关键点：「开心 → 悲伤」在全部 10 种干扰下都是 0.0%。** 用户报告的症状消失。

> clean 那行 n=240 子集上 97.5% → 95.4% 属于抽样噪声（开心只有 80 张，±2 张 = ±2.5pp），

> 95.7% vs 95.3%。所以这不是"用干净精度换鲁棒性"，是两头都变好。

## 4. 已经排除掉的方向（别再试）

| 方向 | 为什么排除 |
|---|---|
| 光照归一化 / 白平衡补偿 | `dark/flat/wb_*` 实测全在 97.5% 以上 |
| 调整前端裁剪比例来救开心 | 前端只偏 2.1px，代价 ≈1pp；位置误差 4px 才致命，靠调参救不了 |
| 输入尺寸（96 是实测最优） | 尺寸扫描：`64→43.6% / 96→95.1% / 128→54.9% / 224→40.0%` |
| 锐化补偿（unsharp） | 干净样本掉点（95.6%→94.4%），不值得 |
| TTA（锐化平均 / 水平翻转平均） | 干净不掉点但收益有限，而推理成本 ×2，直接与"刷新要快"冲突 |
| 降低"开心"的判定阈值 | 属于事后改阈值，会制造假阳性；且不解决根因 |

## 5. 第二轮：「中性和悲伤分不出来」—— 不是回归，是没被优化过的一环

用户接着反馈：**中性和悲伤分不出来**。先把"是不是第一版微调导致的回归"查清楚：
把两级模型放在**同一套退化**上，按"真实类别 → 去向"逐行拆开（validation n=240）。

**真 sad 的去向**（→中性 / →开心 / →悲伤）：

| 干扰 | 微调前 | 第一版 | **第二版（入库）** |
|---|---|---|---|
| clean | 1.2% / 0% / 98.8% | 2.5% / 0% / 97.5% | **1.2% / 0% / 98.8%** |
| **webcam（叠加）** | **47.5%** / 2.5% / 50.0% | **33.8%** / 8.8% / 57.5% | **3.8%** / 5.0% / **91.2%** |
| blur2 | 30.0% / 1.2% / 68.8% | 2.5% / 1.2% / 96.2% | 2.5% / 1.2% / 96.2% |
| halfres | 2.5% / 1.2% / 96.2% | 5.0% / 0% / 95.0% | 2.5% / 0% / 97.5% |
| thirdres | 2.5% / 0% / 97.5% | 2.5% / 0% / 97.5% | 2.5% / 0% / 97.5% |
| jpeg30 | 1.2% / 0% / 98.8% | 1.2% / 0% / 98.8% | 2.5% / 0% / 97.5% |
| shift_up4 | 1.2% / 0% / 98.8% | 1.2% / 0% / 98.8% | 0% / 0% / **100%** |

**结论：第一版在每一格上都不弱于微调前**，所以不是回归。真正的问题在两个模型都吃亏的
`webcam`（脸偏小 + 略糊 + 偏色 + 噪声 + 压缩**叠加**）：微调前 47.5%、第一版 33.8% 的
真 sad 被判成中性。追因：第一版**选模型**用的鲁棒验证集只有 7 种**单独**干扰，
没有这个叠加场景 —— 它从没被优化过。

### 5.1 第二版的改法

1. 增广里新增**叠加型退化链**（概率 0.45）：降采样 0.5–0.85 → 模糊 0.3–1.3 →
   gamma 0.85–1.3 → 白平衡增益 → 高斯噪声 0–9 → JPEG q20–65；
2. 把 `webcam` / `webcam_hard` 加进**选模型**用的鲁棒验证集（9 种干扰），
   用固定种子的局部 RNG 保证逐轮可比。

### 5.2 第二版结果（四道验收全过）

|---|---|---|
| 1 | 类别排列未变 | 最佳映射仍是 `neutral,happy,sad`，全量 **95.1%** ✅ |
| 2 | 逐干扰去向 | `webcam` 真 sad → 中性 **33.8% → 3.8%**，sad 召回 **57.5% → 91.2%**；**「开心→悲伤」仍全 0.0%** ✅ |
| 3 | 前端代码路径 | **95.8%（575/600），退出码 0** ✅ |
| 4 | torch↔onnx 对齐 | 320 张量严格加载，最大差 2.8e-06 ✅ |

## 6. 尚未验证的部分（如实说明）

- 本文所有干扰都是**构造出来的仿真**，不是用户真实摄像头的画面。它们能定位
  "哪个因素最可能致命"并给出可复现的验收标准，但**不能替代真实采集**。
- 本机没有可用的摄像头抓帧路径（无 ffmpeg），因此**没有采到用户本人的 patch**。
  要把线上精度彻底坐实，仍应采一批带标签的真实 patch（可按上面的干扰类型分层）
  再评估一次模型。
- 4 类（含 `fear`）不在本次范围内：`testing/fear` 606 张只有测试集，
  训练数据本机不存在，要 4 类必须重新取数。
