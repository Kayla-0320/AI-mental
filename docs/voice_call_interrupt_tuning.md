# AI 通话：说话被截断 / 打断太快 —— 参数与手动出口

> 起因（用户反馈，2026-10-11）：**"AI 电话的时候录入用户声音的时候还是截断得太快了"**。
> 处理方式：① 把自动判停放宽（服务端端点规则）；② 自动打断加确认窗口（客户端）；
> ③ 新增用户手动「打断并发送」。三件事配套，缺一件都会把体验从"被截断"换成"像对讲机"。

本文是这三处改动的**权威记录**：改了哪个常量、实测是多少、代价是什么、怎么复测。
研究阶段的建议值（`voice_call_research.md` §3 / `voice_call_plan.md` §3 建议把
rule2 压到 **0.40 s**）已被这次的产品判断**推翻**，那两份文档里的旧值不再代表现状。

---

## 1. 一句话结论

| 位置 | 改之前 | 改之后 | 效果（实测） |
|---|---|---|---|
| 服务端端点 `rule1`（说话前静音） | 1.6 s | **2.0 s** | 一起决定有效阈值，见 §2 |
| 服务端端点 `rule2`（说话后静音） | 0.8 s | **1.8 s** | 尾随静音 **1.00 s → 2.00 s** 才定稿 |
| 客户端自动打断 | 第一条 partial 立即掐停 | **持续 0.6 s 才掐停** | 一声咳嗽/换气不再切掉 AI 整句 |
| 客户端手动 | 无 | **「打断并发送」按钮** | 立刻停播 + 立刻定稿，**零等待** |

## 2. 自动判停：服务端端点规则（`algorithm/asr/streaming.py`）

### 2.1 实测数据（不是推算）

```
& '.venv\Scripts\python.exe' algorithm/tools/measure_endpoint_rules.py `
    --rules 1.6/0.8 1.8/1.5 2.0/1.8 --gap 0.8
```

素材：`algorithm/models/asr/sherpa-onnx-paraformer-zh-small-2024-03-09/test_wavs/0.wav`
（5.61 s，最后一个有声块在 5.20 s，尾部自带 0.4 s 静音），逐 100 ms 喂入。

| rule1 / rule2 | 尾随静音多久定稿 | 句中停 0.8 s 会被切开吗 |
|---|---|---|
| 1.6 / 0.8（改之前） | **1.00 s** | **会** |
| 1.8 / 1.5（备选） | 1.70 s | 会 |
| **2.0 / 1.8（采用）** | **2.00 s** | **不会** |

### 2.2 ⚠️ 反直觉的一条：有效阈值 ≈ `min(rule1, rule2)`

这一版 sherpa-onnx 里，**两条规则在"说过话之后"都会生效**。所以：

```
rule1=1.6 / rule2=2.4   →  实测仍然只有 1.7 s（被 rule1 卡住）
rule1=2.0 / rule2=1.8   →  2.00 s
```

**改这一个参数时必须两条一起看。** 只调 rule2 是上一轮的做法，也是这次
"感觉还是太快"的原因之一。

### 2.3 代价，以及为什么可以接受

用户说完 → AI 接话多等约 1 s。加上 LLM/TTS 首声预算，轮次间隔明显长于
`voice_call_research.md` §3 建议的 300–600 ms —— 这是**刻意压过研究文档的产品判断**：

* 中文口语里"我想想……然后……"的停顿普遍 0.6–1.2 s，被判成句末时用户要**重复一遍**，
  还会让算法层拿到一个被切断的半句去分析；
* "被多等半秒"只是慢，"被截断"是没被听见 —— 后者更伤。

### 2.4 真机调参（不用改代码）

```powershell
$env:ASR_RULE1_SILENCE_S = '2.4'
$env:ASR_RULE2_SILENCE_S = '2.2'
# 重启算法服务后复测：
& '.venv\Scripts\python.exe' algorithm/tools/measure_endpoint_rules.py --rules 2.4/2.2
```

非法值（非数字/非正数）不抛异常，回落默认值并打一条 warning —— 一个打错的
环境变量不该让 ASR 服务起不来。

> 作用域：**只影响端点模式（通话页）**。聊天页语音输入是整段录入模式，
> 从不看端点（`StreamingSession.accept()` 的分支），行为不变。

## 3. 自动打断：加 0.6 s 确认窗口（`client/src/hooks/useVoiceCall.ts`）

改之前是"第一条非回声 partial 就 `stopAll()`"。问题是 **partial 的性质**：
它是解码器"刚听到一点"就吐出来的中间结果（首条约在开口后 700 ms，之后每 ~330 ms），
一声咳嗽、一次换气、一次家具响动都可能先吐一条 —— 于是 AI 的句子被切在半句上。

现在：第一条非回声 partial 只是**候选**，`BARGE_IN_CONFIRM_MS = 600 ms` 之后
才 `commitBargeIn()`（`commitBargeIn` 就是原来那段打断逻辑，被抽出来给自动/手动共用）。

* 计时器**不重置**：窗口从"第一次开口"算起，否则一个一直说话的插话者会让 AI 永远说不完。
* 换轮（`runTurn` 开头）、本轮结束（`finish`）、挂断（`endCall`）、卸载都会清掉这个
  定时器 —— 否则它会在下一轮里凭空打断一次（跨轮串味）。
* **判据本身没动**：回声过滤阈值、`retireAll`、`interruptStopMs` 的算法全部不变，
  `S5.5` 的"判定为真打断 → 本地静音 < 200 ms"依然成立（量的是判定之后那一段）。

## 4. 手动「打断并发送」

### 4.1 交互

通话页控制栏（摄像头与挂断之间），`data-action="interrupt-send"`：

* 聆听时高亮（主色）—— 这是"我说完了，该你了"的主动作；
* 提示语：*说完了就点它：小安立刻停下来，你已经说出口的话马上发出去，
  不用等停顿判停（自动判停会等到 1.8 秒静音）*；
* AI 说话时也可以点 = **手动抢话**。

### 4.2 代码路径（3 个文件，各司其职）

| 文件 | 加了什么 |
|---|---|
| `client/src/services/streamingAsr.ts` | `flushSegment()`：向服务端发 `{"type":"finalize"}` 控制帧，**不拆连接、不关麦克风** |
| `client/src/hooks/useVoiceAnalysis.ts` | `flush()`：把 `flushSegment()` 透出去（没有会话/连接没就绪时返回 false） |
| `client/src/hooks/useVoiceCall.ts` | `interruptAndSend()`：`commitBargeIn()` → `flush()`，并暴露给页面 |
| `client/src/pages/patient/VoiceCall.tsx` | 按钮本身（页面仍然"只负责看和点"） |

### 4.3 顺序为什么是"先打断、再定稿"

定稿依赖的音频**已经在服务端**，不受打断影响；反过来做也可以，但会让
"按下按钮 → AI 还在响"多存在一次网络往返。手动打断的体感要求是零等待
（与自动打断共用同一条同步 `stopAll()` 路径）。

### 4.4 边界（都实际走过一遍）

| 情况 | 行为 |
|---|---|
| 本轮还在飞（SSE 没收完） | 打断 + 定稿 → 文本**排队**，等 `done` 之后作为下一轮发（F-4：不 abort、不并发） |
| 本轮已结束 | 打断是空操作，定稿后**立刻开新一轮** |
| 一个字都还没说 | 服务端定稿返回空文本的 final → 前端只清临时候选，**不会编出假句子**（有单测） |
| 落在 400 ms 半双工窗口内 | 送帧已暂停，那段音频服务端没有 → 定稿为空；但打断照常生效（AI 立刻停） |
| 已挂断 | 按钮禁用；`interruptAndSend` 也会直接返回 |
| 危机态 | 按钮可用（语音已禁用），此时它等价于"把我说的话立刻作为文字轮发出去" |

> 服务端侧：`StreamingSession.finalize()` 定稿后会 `_start_new_segment()`，
> 下一次送帧自动开新的一段 —— 所以按一次之后**还能接着说**。
> 这是它与 `stop()`（挂断用，会永久关掉送帧）的根本区别，有单测守着。
