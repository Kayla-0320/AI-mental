# TTS 可行性 benchmark（S0 实测报告）

> 这份文档回答一个问题：**「Path A（本地 ASR + 云端 LLM + 本地 TTS）」到底成不成立。**
>
> 它是 [`call_implementation_steps.md`](./call_implementation_steps.md) **S0** 的执行结果，
> 也是 [`voice_call_plan.md`](./voice_call_plan.md) §5 阶段 0 那道 go/no-go 闸门的答案
> —— 那道闸门在本文档之前**从未跑过**，`voice_call_plan.md` §7 未验证项 2 记的
> "fanchen-C 本机 CPU RTF ≈ 0.15–0.25 **[估计]**，是全篇最重要的未验证数字"，
> 现在被实测替换。

---

## 0. 结论

| 判据 | 结果 | 判定 |
|---|---|---|
| **RTF < 0.4**（空载） | 最差 **0.180**（4 线程）／ **0.112**（8 线程） | ✅ |
| **RTF < 0.4**（满载：同时跑 16kHz 流式 ASR） | 最差 **0.209**（4 线程）／ **0.136**（8 线程） | ✅ |
| 最短句整句合成 < 400 ms（满载） | 507 ms（4 线程）／ **336 ms**（8 线程） | ⚠️ 4 线程不过、8 线程过 |
| 模型能否下载、加载、出声 | 137.7 MB 落盘，加载 0.6 s，能合成 | ✅ |

**结论：Path A 在技术上成立 —— RTF 有 2–3 倍余量，不是一个临界值。**
按 8 线程配置，合成速度是播放速度的 **7 倍**，播放队列在结构上不可能饿死。

**但首声延迟是另一回事（见 §5）**：实测 TTS 对首声的贡献是 **264–477 ms**，
总首声中位 ≈ **1.6 s**。这与 `voice_call_plan.md` 的 [估计] 值几乎一致，
但那是因为两个错误相互抵消（见 §1 的发现一）。

## 1. 三个实测发现（都会改变施工单）

### 发现一：VITS 经 `OfflineTts` **不流式** —— callback 恒为 1 次

`voice_call_plan.md` §2.2 第 7 行假设「TTS 首块 100–300 ms，边合成边推 PCM」。
**实测这个假设不成立**：

```
[短句] 字数=9     callback 次数 = 1   t=282.6 ms  samples=17058
[长句] 字数=33    callback 次数 = 1   t=1012.4 ms samples=64058
```

* callback 对每一句**只被调用一次**，携带的是**整句合成完**的完整音频；
* 且回调收到的样本与 `generate()` 返回的 `audio.samples` **逐样本相等**
  （长度相同、最大差值 0.0）—— 没有任何增量输出。

**影响：**

1. **「首块」就等于「整句合成耗时」**，两者不是两个数。原判据「首块 < 250 ms」
   是为流式合成定的，在非流式下**结构性不可达**（最短的 9 字句也要 263 ms）。
   本文档把该判据改为 **「最短句整句合成 < 400 ms」**。
2. 施工单 S1 的 WS 协议从"分块推流"简化为"**一次一个二进制帧**"（见 §6）。
3. 要压低首声，唯一的手段是**应用层把首句切得更小**（见 §6 的"分块流水线"）。

### 发现二：VITS 的音频时长是**随机的**

同一句话、同一配置，音频长度在多次运行之间会变：

| 文本 | 观测到的音频时长 |
|---|---|
| `听起来这段时间你过得挺不容易的。`（16 字） | 3923 / 4004 / 4101 / 4218 / 4368 ms |
| `听起来这段时间你过得挺不容易的。能和我说说吗？`（2 句） | 3945 / 5938 / 6125 ms |

VITS 的时长预测器带噪声（`noise_scale` / `noise_scale_w`），这是模型性质，不是 bug。

**一个直接后果（实测）**：8 线程下同一句 9 字文本，
`--repeat 5` 取中位数得 **263.0 ms**，而 `--repeat 1` 单跑得 **406.8 ms**
（±55%）。**单次测量会让"最短句 < 400 ms"这条判据随机翻红/翻绿。**

**影响：**

* **RTF 单次测量不可信**，必须重复取中位数（本报告的 `--repeat 5`，下限 3）。
  下表的「audio 波动」列就是把方差摊开给人看，而不是藏起来。
* `AGENTS.md` 的「随机种子固定 42」针对的是**模型初始化与数据划分**的可复现性，
  TTS 时长不在其列 —— 但它确实让"同一句话两次生成的音频不同"。
  若答辩需要严格可复现，可把 `noise_scale` 调低/置 0（**未验证**，本报告没测，
  也没听过它对音质的影响）。**这是一个待决项，不是一个 bug。**
* **顺带一个工具坑**：sherpa-onnx 的 C++ 日志（`Ignore OOV 'CBT'`）走 **stderr**，
  在 PowerShell 里会被当成 `NativeCommandError`，于是**脚本明明返回 0（通过）
  也会显示 `[exit code: 1]`**。判断通过与否要看输出里的 `✅ PASS`，
  或以 `Start-Process -PassThru` 取真实退出码（通过=0、不通过=2）。

### 发现三：`max_num_sentences=1` 会**静默丢弃第一句之后的所有内容** ⚠️

这是三个发现里**最危险**的一个，也是最容易在评审现场翻车的。

`voice_call_plan.md` 与最初的施工单都打算把 `max_num_sentences` 设成 1
（理由："我们自己按句切，不让它再切"）。**实测这个配置只合成第一句：**

| `max_num_sentences` | 1 句 16 字 | 2 句 37 字 | 4 句 66 字 | 4 句文本的 callback 次数 |
|---|---|---|---|---|
| **1** | 4218 ms | **4231 ms** | **4258 ms** ← 后 3 句消失 | 1 |
| 2 | 4218 ms | 6228 ms | 6414 ms | 1 |
| 3 | 4218 ms | 9030 ms | 9546 ms | 1 |
| 4 | 4218 ms | 9030 ms | 11752 ms | 1 |
| 8 | 4218 ms | 9030 ms | **16434 ms** | 1 |
| 100 | 4218 ms | 9030 ms | 16434 ms | 1 |

**66 字、4 句话的文本被合成了 4258 ms —— 与 16 字单句的 4218 ms 几乎一样长。**
没有异常、没有日志、没有报错，只是**少念了三句**。

**正确配置：`max_num_sentences = -1`（不限制）。** 实测 `-1` 与 `100` 结果一致
（都产出完整的 16434 ms）。

> 为什么会踩到：本项目安全闸门（`_StreamingSafetyGate.feed()`）保证**每个 `delta`
> 是一个完整句**，所以"逐句送"时 `mns=1` 看起来"能用"。但**不是所有路径都逐句**：
> SSE 的 `revise` 事件携带的是**整段改稿**，模板兜底（`_generate_empathy_reply`）
> 返回的也是**多句整段**。这些路径会静默只念第一句。
> 这正是本项目最怕的"静默失效"类型（参见 `docs/video_call_build_plan.md` §8.5
> 记的 8001 用错解释器事故：服务正常、`/health` 200、只有 ws 404）。

### 附带发现：词表里**没有拉丁字母**，`CBT` / `HELLO` 会被吞掉

`vits-zh-hf-fanchen-C` 的 `lexicon.txt` **不含任何 ASCII 字母**，合成时会打：

```
character-lexicon.cc:ConvertTextToTokenIds:181 Ignore OOV 'CBT'
character-lexicon.cc:ConvertTextToTokenIds:181 Ignore OOV '-'
```

对一个心理学产品来说这很实际：回复里出现 `CBT`（认知行为疗法）时，
**这个词会被完全跳过**，用户听到的是"我们试试 里的一个方法，叫做认知重构"。

**对策（施工单 S1 要落）**：送 TTS 之前做一次**中文替换**，把常见术语/缩写换成
可发音的中文（`CBT` → `认知行为疗法`）。这是一张**小映射表**，属于话术层，
不涉及安全规则。数字与电话走 `number.fst` / `phone.fst` 正常（`400-161-9995`
的 `-` 被忽略但数字读得出来）。

| 6 | **TTS 首个 unit 整句合成** | **0.263 – 0.477 s**（9–16 字，8 线程） | **[实测-本机]** |
| 7 | 下行 + 起播 | 0.040 – 0.080 s | [估计] |
| | **合计首声** | **≈ 1.35 – 1.97 s（中位 ≈ 1.6 s）** | [估计，含实测项] |

**这个结论与 `voice_call_plan.md` §2.4 一致，实测没有推翻它。**

## 6. 对施工单的影响（S1 / S2 / S4 要改的地方）

### 6.1 S1：协议简化 + 两个必须落死的配置

**协议简化**：既然 callback 只给一次完整音频，`/tts/ws` 的帧序列退化为：

```
client → {"type":"say","seq":1,"text":"..."}
server → {"type":"start","seq":1,"sample_rate":16000}
         一个二进制帧（整句 int16 PCM）
         {"type":"end","seq":1,"audio_ms":..,"synth_ms":..,"rtf":..}
```

原来的"多块二进制 + start/end 定界"设计**不再需要**（但 `start`/`end` 仍要保留：
客户端要能区分"这一帧属于哪一句"，以及"这一句结束了"）。
线程池/`call_soon_threadsafe` 的形态不变 —— 合成仍是 CPU 密集、仍不能占事件循环。

**必须落死的两个配置：**

| 配置 | 值 | 不这么做的后果 |
|---|---|---|
| `max_num_sentences` | **`-1`** | 只念第一句，其余静默丢弃（发现三） |
| `num_threads` | `clamp(核数-2, 2, 8)` | 1 线程时 RTF 0.568 → **直接不达标** |

**必须新增的回归测试**（就是发现三的复现方式）：
把一段 N 句文本**整体送一次**与**逐句送 N 次**，断言两者音频总时长接近。
`mns=1` 会让前者 ≈ 单句时长，测试立刻红。

### 6.2 S2/S4：应用层分块 + 合成/播放流水线（把非流式的影响消掉）

RTF ≈ 0.11–0.14 意味着**合成比播放快 7 倍**。因此：

```
首句文本就绪 → 立刻送 TTS（不等后续句子）
   ↓ 合成 ~300 ms
开始播第 1 块 ──同时──→ 合成第 2 块
   ↓ 播第 1 块（~2.4 s）
播第 2 块 ──────同时──→ 合成第 3 块
```

只要"分块"比"播放"快，队列永不断流。**这把非流式 TTS 变成了流式体验**，
代价只在**第 1 块**：必须等它合成完才能出声。

**因此首声优化的具体手段 = 让第 1 块尽量短：**

* 第 1 个 unit 若 > 12 字，**按逗号再切一刀**（`，,、：:`），只送第一个小句去合成；
* 例：`听起来这段时间你过得挺不容易的。`（16 字，443 ms）
  → 若首句是 `我听到你说最近晚上都睡不好，这种感觉真的很难熬。`
  则第 1 块 = `我听到你说最近晚上都睡不好，`（13 字 ≈ 400 ms）——
  省下的不是很多，但**这是唯一能压的地方**，而且零风险、不碰安全组件。

### 6.3 S1：送 TTS 前的中文替换表（发现四的对策）

    "WHO": "世界卫生组织",

## 9. 一页速览

1. **Path A 成立。** RTF 最差 0.180（4 线程）/ 0.112（8 线程）空载，

## 10. 音色与模型对比（人耳反馈"难听"之后的排查）

**起因**：S1/S2 做完后请人试听，反馈**"声音好难听"**。
本文档 §7 未验证项 7 早就把"中文音质好不好听"标成"只能由人验证"，
现在验证结果是不合格。以下是排查与结论。

### 10.1 第一发现：`num_speakers = 187` 是真的，而默认 sid=0 是**最慢**的那个

一开始怀疑 `num_speakers=187` 是我读错字段。实测否掉了这个怀疑 ——
9 个 sid 产出 **9 种完全不同的波形**：

| sid | 同一句话的音频时长 |
|---|---|
| **0（默认，一直在用的）** | **4389 ms** ← 最慢 |
| 1 | 2593 ms |
| 100 | 2459 ms |
| 150 | 3356 ms |
| 186 | 3330 ms |

**结论：换音色的第一选择是换 `sid`，不是换模型。** 187 个音色的试听带：
`_tts_bench/voices/audition_all.wav`（10 分 04 秒，带时间戳表）。

### 10.2 第二发现：同系列模型不是同一档位 —— 采样率差了一整档

下载了同系列的 `theresa` / `eula` 对比，发现它们**不是同一条流水线的产物**：

| 模型 | 采样率 | 说话人数 | 空载 RTF | 满载 RTF | 最短句（满载） |
|---|---|---|---|---|---|
| `vits-zh-hf-fanchen-C`（原用） | **16000 Hz** | 187 | 0.112 | 0.136 | 336 ms |
| `vits-zh-hf-theresa` | **22050 Hz** | **804** | 0.160 | **0.232** | 319 ms |
| `vits-zh-hf-eula` | **22050 Hz** | **804** | 0.182 | **0.243** | 325 ms |

**16 kHz → 22 kHz 是实打实的档位差**（16 kHz 的带宽上限就是"闷"的来源之一），
音色库也从 187 涨到 804。而 **RTF 依然只有 0.23，两条判据全过** ——
**这里没有任何需要权衡的地方**。

### 10.3 换模型时踩到并修掉的一个**静默降级** bug ⚠️

设置 `TTS_MODEL_DIR` 指向 `theresa` 后，`/tts/status` **仍然报 `vits-zh-hf-fanchen-C`**。

根因是 `tts/engine.py` 里我自己写的一行：

```python
REQUIRED_FILES = (f"{MODEL_NAME}.onnx", ...)     # MODEL_NAME 写死成 fanchen-C
```

`theresa` 目录里的 onnx 叫 `theresa.onnx` → `_usable()` 判它**不可用** →
`resolve_tts_model_dir()` 靠"逐个候选试一遍"的写法**无声地回退到默认模型**。
调用方只看到"换模型没生效"，日志里一个字的抱怨都没有。

**这正是本项目反复踩的同一类坑**（8001 用错解释器只剩一个端点坏、
`max_num_sentences=1` 静默截断）。已按同一条原则修掉：

1. **onnx 按目录内容识别**（`_find_onnx`），不写死文件名；同时存在 int8 与完整版时优先完整版。
2. **显式指定 ≠ 建议**：`TTS_MODEL_DIR` 或显式路径不可用时**直接失败并说明缺什么**，
   **绝不回退**到别的模型。
3. `status()` 的 `model_name` 报**实际加载到的目录名**，不是默认模型名 ——
   否则"换模型没生效"在状态里根本看不出来。
4. 新增 8 条 `TestModelDirResolution` 测试守这些行为（含"显式坏路径不得回退"）。

### 10.4 换到 22 kHz 之后：客户端**一行没改**

这一点是 S1/S2 分层的价值所在，已用浏览器实测证明（`_probe_tts_player.js`）：

| 项 | 16 kHz（fanchen-C） | 22 kHz（theresa） |
|---|---|---|
| S2 闸门 | 17/17 通过 | **17/17 通过** |
| 端到端首声 | 347 ms | **237–272 ms** |
| 句间排程偏差 | `[0,0,1,-1]` ms | **`[0,0,0,0]` ms** |
| 5 句总墙钟 | 19.8 s | **13.1 s** |

客户端之所以不用改，是因为三处都**没有假设采样率**：
`ttsStream` 用服务端帧里带的 `sample_rate`、`TtsPlayer` 用 `ctx.createBuffer(1, len, sampleRate)`
（由浏览器重采样到设备率）、`tts_benchmark` 报的是模型自述值。

### 10.5 剩下的只有一件事：**用哪个人声，只有人耳能定**

已生成的试听材料（都在 `_tts_bench/voices/`）：

| 文件 | 内容 |
|---|---|
| `audition_all.wav` | fanchen-C 全部 **187** 个音色，10 分 04 秒，带时间戳表 |
| `models/audition_vits-zh-hf-theresa.wav` | theresa 抽听 12 个音色，35 秒 |
| `models/audition_vits-zh-hf-eula.wav` | eula 抽听 12 个音色，33 秒 |
| `models/<模型>_sidNNN.wav` | 单个音色，圈定后细听 |
| `speed_*.wav` / `length_*.wav` / `noise_*.wav` / `noisew_*.wav` | 参数扫描（语速/时长/噪声） |

**判断标准不是"好听"，而是"像不像一个耐心的人在听你说话"。**

### 10.6 如果 187 + 804 个音色都不满意

那就不是"选哪个音色"的问题，而是 **16/22 kHz VITS 这个技术档位的天花板**问题。
那时的选项是：

| 选项 | 代价 | 说明 |
|---|---|---|
| 云端 TTS | 网络依赖、计费、一次网络往返 | **不违反"数据不出设备"** —— 见 `call_implementation_steps.md` §11 的论证：发出去的是 AI 自己的回复文本，而它本来就在云端 LLM 上生成；用户的**语音**一个字节都不出去 |
| 换更高档的本地模型 | 体积/算力 | 需要另找（本报告只覆盖了 `vits-zh-hf-*` 系列与 piper） |
| 接受现状 | 无 | 16 kHz 相当于电话音质（真电话是 8 kHz），"能听清"是够的，"好听"不够 |

**迁移成本很低**：`TtsPlayer`（S2）与客户端协议都不用改，
只需在 `algorithm/tts/engine.py` 旁边加一个云端实现，由配置选。
