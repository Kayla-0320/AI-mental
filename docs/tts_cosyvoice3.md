# CosyVoice3 接入纪要（含三个代价很大的坑）

> 本文档记录 2026-10-05 把 **CosyVoice3 零样本音色克隆**接进语音通话的完整过程。
>
> 重点不是"接了什么"，而是**三个花了数小时才认出来的坑**。它们的共同特征是：
> **现场表现和日志内容都对不上真正的原因** —— 一个是服务"一启动就崩"却没有任何
> Python 回溯，一个是"延迟指标变好了但用户说难听"，一个是"单次 A/B 测出两个
> 互相矛盾的结论"。
>
> 前序文档：[`tts_benchmark.md`](./tts_benchmark.md)（VITS/Qwen3 的 S0 实测）、
> [`voice_call_plan.md`](./voice_call_plan.md)、
> [`call_implementation_steps.md`](./call_implementation_steps.md)。

## 0. 一页速览

| 项目 | 值 |
|---|---|
| 模型 | `Fun-CosyVoice3-0.5B`，24 kHz，零样本克隆 |
| 参考音 | `algorithm/tts/cosyvoice_service/prompt_qwen3_voice.wav`（262 KB，仓库内） |
| 部署形态 | **独立微服务**，HTTP `127.0.0.1:8002` |
| 算法侧接入 | `.env` 里 `TTS_BACKEND=cosyvoice` |
| 启动 | `npm run dev:tts` |
| 核对是否真的生效 | `GET http://127.0.0.1:8001/api/v1/tts/status` → `"engine": "cosyvoice3"` |
| 首块延迟（浏览器路径） | **2.2–2.3 s** |
| 加载峰值提交内存 | **约 9.6 GB**（需要系统余量 ≥ 13 GB 才稳） |
| 加载耗时 | 约 22–26 s（首次请求触发，之后常驻） |

**三个坑的一句话版：**

1. **提交内存耗尽会表现为原生访问冲突**（`c10.dll`／`fbgemm.dll`／`torch_cpu.dll`，
   `0xc0000005`），**日志里一行 Python 回溯都没有**，而且失败后进程还残留数 GB
   提交内存，把下一次尝试推得更死。严重时连 `dwm.exe` 一起崩。
2. **`token_hop_len` 是"首块延迟 vs 音质"的直接取舍**。为了首块快 0.5 秒把它压到 10，
   换来的是声码器上下文从 1.24 s 缩到 0.24 s —— 用户听到的是**金属味 + 断续**。
   **延迟指标好看不等于体验好。**
3. **CosyVoice 是随机采样，单次生成的 A/B 结论不可信**。同一句话两次生成的时长能差
   23%、F0 中位数能差 26 Hz。必须先固定随机种子并验证可复现，否则测出来的差异
   大部分是噪声。**我曾据此得出两个互相矛盾的结论。**

## 1. 为什么做成独立微服务

CosyVoice3 与算法服务的依赖**直接冲突**，放不进同一个解释器：

| | 算法服务 | CosyVoice 服务 |
|---|---|---|
| torch | 2.11 | **2.7.0+cu128** |
| numpy | 2.5 | **< 2** |
| transformers | 新版 | **4.51.3** |

所以做成独立进程 + 独立 venv，算法侧用同步 HTTP 调用
（`algorithm/tts/cosyvoice_engine.py`）。这与项目既有的"ASR 与 TTS 分开上报"
是同一条原则：**依赖与失败模式独立**。

> 另有历史原因：本机驱动是 sm_120，cu121 的 torch 会报
> `CUDA error: no kernel image is available`，必须 cu128。

### 1.1 算法侧怎么切，以及为什么必须核对

`.env`（仓库根，已被 `.gitignore` 忽略）：

```ini
TTS_BACKEND=cosyvoice
COSYVOICE_API_URL=http://127.0.0.1:8002
COSYVOICE_SPEED=1.2
TTS_SPEED=1.2
```

⚠️ **`TTS_BACKEND` 拼错会静默回落到 vits** —— 现场表现就是"换了音色但听起来没变"。
本项目此前踩过这个坑，所以 `create_engine()` 对未知值**同时**记 warning 与 info，
且 `/tts/status` 会如实报出**实际生效**的引擎名。

**换引擎后一定要核这一条**：

```bash
curl http://127.0.0.1:8001/api/v1/tts/status    # engine 必须是 cosyvoice3
```

`TTS_SPEED` 也值得单独说：`/tts/ws` 的会话默认语速来自它，而**客户端从来不发
`speed` 字段**（见 `client/src/services/ttsStream.ts` 的 `say` 帧）。不设的话会话
`status` 帧会报 `1.0`，而实际出声是 `COSYVOICE_SPEED` 的 1.2 —— 排查时会误导。

### 1.2 启动：`npm run dev:tts`

与 `run-algorithm.mjs` 同样的思路（**启动前挡住会让它静默失效的情况**），
`scripts/run-tts.mjs` 有三道闸门：

1. **解释器**必须是 CosyVoice 自己的 venv（用算法服务的解释器会因 torch/numpy 冲突失败）；
2. **依赖**齐全（fastapi / uvicorn / torch / onnxruntime）；
3. **提交内存余量**足够 + 8002 上没有已在跑的服务。

> 第 3 条里的"端口已占用"检查不是多余的：**同时起两份会在加载阶段把提交内存吃穿
> 并原生崩溃**（实测踩到两次）。端口上有服务时先问 `/health`，不要盲目再起一份。

## 2. 坑一：提交内存耗尽 = 原生崩溃，没有 Python 回溯 ⚠️

### 2.1 现场表现

用户的原话是"**Docker 一启动就崩**"、"**服务一启动就崩**"。实际观察到的现象：

```
ONNX Runtime:  bad allocation
               Load model from speech_tokenizer_v3.onnx failed: bad allocation
Python:        OSError: 页面文件太小，无法完成操作。 (os error 1455)
Windows 事件日志:
  python.exe   崩于 c10.dll       异常代码 0xc0000005
  python.exe   崩于 fbgemm.dll    异常代码 0xc0000005
  python.exe   崩于 torch_cpu.dll 异常代码 0xc0000005
  dwm.exe      崩于 dwmcore.dll   ← 桌面窗口管理器一起崩
  msedge.exe   崩于 KERNELBASE.dll
  DSH 宿主      exit 3758096392
```

**服务日志里没有任何 `Traceback`。** 因为访问冲突（`0xc0000005`）不是 Python 异常，
`try/except` **拦不住** —— 进程被操作系统直接终止，缓冲区里的输出也一起丢失。

> 附带一个排查陷阱：Python 的 stdout 重定向到文件时是**块缓冲**的，原生崩溃会丢掉
> 整个缓冲区。所以"日志最后一行"**不代表真实死点**，可能死得更晚。用 `python -u`
> 或 `PYTHONUNBUFFERED=1` 才能看到真实位置。

### 2.2 病因

```
物理内存            31.4 GB
页面文件 C:\pagefile.sys  4096 MB   ← 被手工固定，AutomaticManagedPagefile = False
─────────────────────────────────
提交上限            35.4 GB
```

整套服务需要约 **39 GB**，缺口约 4 GB。而"提交内存"是**先记账后给钱**的模型：
程序申请内存时 Windows 先在账本上记一笔，**即使这笔内存从没被真正用过**。所以会出现
反直觉的现象：

```
物理内存剩余  6.9 GB      ← 看着还挺空
提交内存余量  368 MB      ← 账本已经满了
```

两个数不矛盾：柜子还空着，但"已承诺留位置"的订单把额度占满了。

### 2.3 为什么这个坑特别贵

**失败后进程不会释放已占的内存。** 实测一次加载失败会残留 **7.3 GB** 提交内存，
于是下一次尝试余量更少，**越试越死**。这也是"反复重试反而更容易整机崩"的原因。

`os error 1455` 就是 `ERROR_COMMITMENT_LIMIT`（页面文件太小）—— **这是唯一一句
人话报错**，其余全是硬崩。看到它就该直接去查页面文件，不要再猜代码。

### 2.4 确认与定位方法

```powershell
# 提交上限 / 已用 / 余量
Get-CimInstance Win32_PerfFormattedData_PerfOS_Memory |
  Select-Object CommitLimit, CommittedBytes

# 页面文件配置（Fixed 且非系统托管就是元凶）
Get-CimInstance Win32_PageFileSetting | Select-Object Name,InitialSize,MaximumSize
(Get-CimInstance Win32_ComputerSystem).AutomaticManagedPagefile

# 原生崩溃（Python 层面看不到的那种）
Get-WinEvent -FilterHashtable @{LogName='Application'; Level=1,2;
  StartTime=(Get-Date).AddMinutes(-20)} |
  Select-Object TimeCreated, @{n='M';e={($_.Message -split "`n")[0..1] -join ' | '}}
```

**判别要点**：同一时间窗内**多个不相关进程**（`dwm.exe`、`msedge.exe`、
`LenovoBaiying.exe`）一起崩 ⇒ 这不是某个程序的 bug，是**整机资源耗尽**。
只盯 CosyVoice 的日志永远查不出来。

### 2.5 已经做的防护

| 措施 | 效果 |
|---|---|
| **加载前预检可提交内存**（`_commit_headroom_mb()`） | 余量不足时返回明确错误，而不是硬上把整机拖崩 |
| 权重 **`mmap=True`** 读取 | fp32 源权重走文件映射，不再整份进匿名内存 |
| **关掉 ONNX BFC 内存池** | `speech_tokenizer_v3.onnx`（924 MB）提交开销 **1990 MB → 909 MB** |
| 先降精度再灌权重 | 模块不再额外持有一份 fp32 |
| `load_state_dict(assign=True)`（仅 llm/flow） | 逻辑上省掉一份 1.9 GB 拷贝；**实测峰值未变**，别当性能优化记账 |
| hift（声码器）保持 **fp32** | 声码器决定音色，量化到 fp16 换来的 40 MB 不值得 |

**加载内存分步实测**（2026-10-05，提交内存口径）：

```
baseline                                     10,574 MB
import torch + onnxruntime                   +1,385 MB
engine singleton                                +13 MB
[onnx] campplus session                         +47 MB
[onnx] speech_tokenizer session                +929 MB
[lsd] CosyVoice3LM            1225.1 MB 权重
[lsd] CausalMaskedDiffWithDiT  633.7 MB 权重
[lsd] CausalHiFTGenerator       39.6 MB 权重
─────────────────────────────────────────────────────
加载完成后常驻                               +6,094 MB
加载全程峰值                                 +9,510 MB   ← 决定成败的是这个
```

**阈值标定**（这是**服务进程内**的读数，检查点在 `import torch` 之后）：

```
观测到原生崩溃时  服务内读数 = 10,997 MB
成功加载时        服务内读数 ≈ 12,000 MB 以上
→ 下限取 12288 MB（COSYVOICE_MIN_COMMIT_MB 可覆盖）
```

⚠️ 注意 `run-tts.mjs` 是在**启动前**读的同一个计数器，此时还没 `import torch`，
所以读数会明显偏高。两处的阈值含义不同，**不要为了让检查通过而调低它**。

### 2.6 根治办法（需要管理员）

> 设置 → 系统 → 关于 → 高级系统设置 → 性能「设置」→ 高级 → 虚拟内存「更改」
> → 勾选**「自动管理所有驱动器的分页文件大小」** → 重启

改完提交上限从 35.4 GB 涨到约 62 GB，缺口 4 GB 变成富余 23 GB，这类崩溃彻底消失。
**在改之前，任何"靠关程序腾内存"都只是顶着。**

## 3. 坑二：`token_hop_len` 是"首块延迟 vs 音质"的直接取舍

### 3.1 数据

`token_hop_len` 决定模型每次产出的音频块多大，也就决定**声码器每次拿到的上下文
有多长**。它同时影响首块延迟和音质。固定种子实测（同一句话、同一 seed，
音频总长都是 3.08 s，唯一变量是 hop）：

| hop | 首块延迟 | 块数 | **最小块长** | 边界跳变倍数 | HF>6kHz | 频谱平坦度 | 谱质心 |
|---|---|---|---|---|---|---|---|
| 8 | 1.74 s | 4 | 0.32 s | 0.743 | 1.53% | 0.03054 | 587.8 Hz |
| **10**（曾采用） | **1.62 s** | 4 | **0.24 s** | 1.446 | 1.57% | 0.03104 | 588.2 Hz |
| 15 | 2.03 s | 3 | 0.84 s | 6.119 | 1.78% | 0.03266 | 623.5 Hz |
| 20 | 1.80 s | 3 | 0.64 s | 0.007 | 2.06% | 0.04332 | 705.5 Hz |
| **25**（模型默认，现用） | 2.13 s | 2 | **1.24 s** | 0.091 | 1.60% | 0.03133 | 594.1 Hz |

### 3.2 怎么读这张表

* **判据是"最小块长"，不是"边界跳变倍数"。** 后者受"边界恰好落在语音还是静音"
  影响，所以不单调（hop=15 反而 6.119），只能当参考。
* hop=10 时声码器第一块只有 **0.24 s**，hop=25 是 **1.24 s** —— **差 5 倍**。
  HiFi-GAN 上下文越短，块边界相位越难接上，现场听起来就是**金属味 + 不连续**。
* 代价只有 **+0.5 s** 首块延迟。这笔账明显划算。

### 3.3 历史教训

早期版本只看"首块 3.20 s → 1.58 s"这个数字就选了 hop=10，**没有量音质代价**。
用户随后反馈："声音有一种很浓的机器人金属味，而且并不连续。"

**结论：延迟指标好看不等于体验好。改任何"让首块更快"的参数之前，必须先量音质，
并且必须由人耳确认。**

需要更快首块时可以设 `COSYVOICE_FIRST_HOP=10` 换回来，但要知道这是在拿音质换。

> hop=3 会崩：flow 的 `pre_lookahead` 越界（`ZeroDivisionError`）。
> 另外 `token_hop_len` 是**引擎单例上的状态**，用完必须 `finally` 还原，
> 否则会污染后续请求且单调缩小。

## 4. 坑三：随机采样让"单次 A/B"毫无意义 ⚠️

### 4.1 方差有多大

同一句话、同样参数，两次生成：

```
音频时长      2.84 s / 3.60 s / 2.73 s      → 波动 ±23%
F0 中位数     214.3 Hz / 240.0 Hz / 216.2 Hz → 差 26 Hz
```

**这个方差比绝大多数我想测的差异都大。**

### 4.2 我犯的错

我曾用"单次生成 A/B"得出两个**互相矛盾**的结论：

| 轮次 | 结论 |
|---|---|
| 第一轮 | "伸缩让 HF 从 0.79% 升到 1.06%，金属味是伸缩造成的" |
| 第二轮（fp32 后） | "HF 从 0.79% 升到 1.15%，fp32 反而更差" |

两个结论都不能成立 —— 它们测的其实是**采样噪声**。

### 4.3 正确做法

固定 `random` / `numpy` / `torch` 的全局种子，并**先验证可复现**：

```python
random.seed(SEED); np.random.seed(SEED)
torch.manual_seed(SEED); torch.cuda.manual_seed_all(SEED)

# 必须先验证，否则后面全是白测
a1 = synth(seed=42); a2 = synth(seed=42)
assert np.array_equal(a1, a2)     # 实测：len 73920 == 73920，逐样本相同
```

验证通过后，同一 seed 下**逐样本相同**，此时 A/B 才有效。

### 4.4 修正后的结论

固定种子重测"逐块伸缩 1.2×"的代价（hop=10，同一 seed）：

| | 时长 | HF>6kHz | 频谱平坦度 | 谱质心 |
|---|---|---|---|---|
| 不伸缩 | 3.08 s | 1.57% | 0.03104 | 588.2 Hz |
| 逐块伸缩 1.2× | **2.57 s** | **0.79%** | **0.01820** | **526.5 Hz** |

**伸缩反而把高频砍半、平坦度和谱质心都降低** —— 它**不是**金属味的来源。
同时确认伸缩的倍率是准确的（3.08 → 2.57 s，正好 1.2 倍）。

> ### ⚠️ 2026-10-05 更正：上面这条结论**是错的**，已被听感判决推翻
>
> 错在哪：HF / 平坦度 / 谱质心这三个量**对相位声码器的"相位涂抹"不敏感**。
> 相位声码器把谐波相位打散，但并不明显抬高总能量里的高频占比，
> 所以这三个指标看不到问题 —— 不是"没有代价"，是"尺子不对"。
>
> **听感判决**（用户，2026-10-05）：`金属_A_模型原始_不伸缩.wav` **没有金属音**；
> 同一批样本过 1.2× 伸缩后**有**。
>
> 换用嗓音学里测"粗哑/金属"的标准量 **CPPS**（倒谱峰突出度，越低越糙）重测，
> 同一批模型样本、唯一变量是伸缩算子：
>
> | 条件 | CPPS | HNR | 46.9 Hz 调制 | 接缝 click |
> |---|---|---|---|---|
> | 不伸缩（模型裸输出） | **4.651** | **6.82 dB** | 5.7 dB | — |
> | 逐块伸缩 1.2×（相位声码器） | **3.952** | **5.33 dB** | 8.6 dB | 99.92%（有） |
> | 逐块伸缩 1.2×（WSOLA，现用） | **4.825** | **6.65 dB** | 7.8 dB | 97%（无） |
>
> CPPS −15%、HNR −1.5 dB，且 **46.9 Hz 处多出一根窄带调制**
> —— 46.9 Hz 正是 `librosa.effects.time_stretch` 默认 `hop=512 @24k` 的帧率，
> 那就是电子/金属声的物理来源。把同一个算子用在**公认干净的真人录音**上，
> 代价一模一样（CPPS 4.223 → 3.898，HNR 6.21 → 5.68）→ 是算子的锅，不是模型的锅。
> 另外逐块相位声码器在块 2→3 接缝处留下了 click（跳变超过全段 99.92% 的同等窗口）。
>
> **处置**：`pitch_safe_resample`（相位声码器）已被 `wsola_time_stretch` 取代
> （`cosyvoice_service/server.py`，`COSYVOICE_SPEED_ALGO` 默认 `wsola`，
> 设 `librosa` 可回滚对照）。逐块调用不掉指标（CPPS 4.793 vs 整段 4.853）、
> 接缝无 click、耗时同级（7.28 s 音频 26 ms，RTF 0.0035）。
>
> **教训**：本文件里"N 次实验得出 X 不是原因"的结论，必须写清**用的是什么尺子**
> —— 尺子测不到，不等于不存在。

### 4.5 指标本身的陷阱

* **"边界跳变倍数"**（块边界处一阶差分 ÷ 整体中位差分）：受边界落点影响，**不单调**，
  只能横向对比同一句话。
* **click 计数**（>med+8MAD 的样点）：正常语音的爆破音也会被算进去，
  实测"不伸缩"反而比"伸缩"多，**不能用来判断伪影**。
* **HF / 频谱平坦度 / 谱质心**：方向性可用，但必须固定种子。

## 5. 遗留问题（**未解决**，别当成已解决）

1. **RTF 仍 > 1。** 浏览器路径实测：hop=10 时 1.27–1.67，hop=25 时 1.27–1.28。
   含义是"合成耗时 ÷ 音频时长 > 1"。
   但 hop=25 的首块自带 **1.24 s** 缓冲，且后续产出速率约为播放的 1.36 倍，
   理论上不会饿死播放队列 —— 而 hop=10 时缓冲只有 0.24 s。
   **播放端 `ttsPlayer.ts:199` 的 `Math.max(ctx.currentTime, this.nextStartTime)`
   在跟不上时会退化成"立刻播"，时间轴上就出现空洞。** 这一条需要人耳确认是否已消除。

   > **2026-10-11 更新**：**不用人耳了** —— 播放空洞现在是实测读数
   > （`ttsPlayer.ts` 的 `TtsUnderrunStats`，通话页 `?debug=1` 的
   > 「音频空洞 / 本轮音频空洞」），判据与复测见
   > `docs/voice_call_audio_stutter.md` §4。
   > 另外那里算了一笔账：**`TTS_SPEED=1.2` 会把 RTF 乘以 1.2**
   > （分母是被缩短的输出时长），1.27 / 1.2 ≈ 1.06 —— 加速本身就是把余量吃掉的
   > 那一步。要不要为音质/流畅换回原速是产品取舍，先量再决定。

2. ~~**金属味的其他可能来源。** 参考音 `prompt_qwen3_voice.wav` **本身是 Qwen3-TTS
   生成的合成语音**，不是真人录音。~~
   **已处置（2026-10-05）**：参考音已换成用户提供的**真人录音**
   `prompt_user_recording.wav`（6.5 s，谱减降噪），合成语音参考音不再是问题。
   金属味的真正来源已定位为**相位声码器**，见 §4.4 的更正块。

2b. **LLM 采样没有定种子（未解决，是当前最大的音色方差来源）。**
   `cosyvoice/llm/llm.py:172` 是 `sampling: int = 25`（top-k 随机采样），
   而全仓库对 `set_all_random_seed`（`cosyvoice/utils/common.py:181`）的调用
   只在 `webui.py` / `vllm_example.py` 里 —— **本服务一次都没调**。
   实测（同一文本、同配置、同服务，直连跑 6 次）：

   | | 时长 | 频谱平坦度(浊音帧) | HF>6kHz(浊音帧) | 峰值 |
   |---|---|---|---|---|
   | 最小 | 5.53 s | 0.00961 | 0.64% | 0.469 |
   | 最大 | 7.40 s | 0.01893 | 1.50% | 0.934 |
   | **极差/均值** | **29%** | **70%** | **81%** | **65%** |

   → 同一句话每次播出来的**音色和音量都在摆**（峰值 0.47–0.93 = 差 6 dB）。
   这既解释了"有时候金属味特别重"，也意味着**本文件里所有 N=1 的 A/B 结论都不可信**
   （例如"合成参考音 0.03133 vs 真人 0.01130"这种差异，小于单次采样的自然摆幅）。
   对策：合成前调 `set_all_random_seed` 并固定到一次干净的 draw，
   或降低 top_k / 温度。**任何音质 A/B 都要么配对同一次生成，要么 n≥5 取中位数报极差。**

## 7. 本报告**没有**验证的事

* **音质好坏没有人耳结论。** 本文档给的是客观指标（HF / 平坦度 / 谱质心 /
  边界跳变）和机制解释。"金属味是否消失"必须由人听。
* **§3 的 hop 表是单句、单 seed 的结果**，未做多种文本/多 seed 的重复实验。
  趋势（最小块长随 hop 单调）可靠，具体数值不可外推。
* **§4.4 的伸缩代价只测了一句话**，未覆盖长句。
* **播放端是否仍会断粮没有实测**：只做了"首块缓冲 + 产出速率"的推算，
  没有在浏览器里量播放队列的空洞。
* **fp16 权重对音质的影响没有独立量化。** hift 改回 fp32 是**基于原理**
  （声码器不该被量化）而非实测收益；llm/flow 仍是 fp16（显存不够放 fp32）。
* **`assign=True` 的实际收益未测出。** 逻辑上省一份 1.9 GB 拷贝，但实测加载峰值
  9,510 → 9,605 MB，**没有变化**。那 3.4 GB 瞬时开销在别处，未定位。
